# 《账本》设计文档

> AI 短剧的叙事一致性账本
> 版本：0.1（设计阶段，未开始实现）

---

## 0. 一句话

**在开拍之前拦下「故事讲错了」，并算出它本来会烧掉多少钱。**

它只做一件事：记住谁在什么时候知道了什么，然后发现有没有人提前知道了。

---

## 1. 要解决的问题

### 1.1 具体场景

一部 60 集短剧：

- 第 3 集，女主对反派说：「你三年前烧了那间仓库，别以为我不知道。」
- 但按剧本，女主**得知这件事是在第 12 集**——她偷听到的。

第 3 集的她不可能知道。这类错误行业里叫**连续性错误**，剧组本来有**场记**（Script Supervisor）专门盯——但场记只能盯现场看得见的东西（衣服颜色、杯子位置）。**「谁在第几集知道了什么」这种跨越 60 集的信息流动，人盯不住。**

这就是本产品要解决的**唯一一件事**。

### 1.2 为什么 skill / 提示词解决不了

| 公司关心的问题 | 答案存在哪里 | skill / 文档能否拿到 |
|---|---|---|
| 问题发生在哪里 | 调用日志、失败记录、版本元数据 | ✗ 不在剧本里 |
| 改动会影响什么 | 一张**真实的**依赖图 | ✗ 模型只能推断，且每次不同 |
| 钱花在哪里 | API 账单、计量数据 | ✗ 读不到没被喂进去的数据 |

更关键：**知识泄漏判定需要跨全剧的持久状态**（谁在第几场知道什么）。隔离上下文每次从零开始读，读不完 60 集，也没有记忆。批处理式 skill 的输出是自由文本，**没有可寻址的实体**，因此 waiver、版本对比、修复追踪、增量复检全都做不了。

### 1.3 一句话与竞品的界限

> **NiliX 告诉你这一帧画崩了；《账本》告诉你这个故事讲错了——以及它已经烧掉了多少钱。**

## 2. 竞品边界

八路调研 + 事实核查的结论。

| 层 | 占用情况 |
|---|---|
| 成本追踪 / 预算告警 | 9 家可观测性工具（Langfuse、Helicone、Phoenix、Braintrust、LangSmith、Weave、Harness CACM、OpenMeter、Lago）+ 爱奇艺纳逗Pro + NiliX |
| 事前成本预估 | footagen.ai、ArcReel、ArcLoop、阿里云公式、Token Forecast |
| 重试浪费度量 | ArcLoop 三本账、dev.to 实测、阿里云 `w` 因子 |
| 改一处 → 受影响产物 | Kumiho（`analyze_impact`）、ArcLoop（`@` 引用）、**NiliX（输入指纹 + stale 四态，最完整）** |
| 画面质量审片 | NiliX 八维度 VLM 判分、footagen continuity |
| **叙事一致性** | **无人** |

**结论：不做成本追踪、不做依赖图、不做失效传播——行业已饱和，直接接。唯一空白是「判断故事讲得对不对」。**

需要警惕的两个竞品：

  ⚠️ **真实风险是话术占位**：该站为 SEO 内容农场（8 月单月约 2 篇/日、共约 170 篇），已把「改剧本 / 受影响镜头 / 返工成本」长尾词铺满。**对策是自落硬证据**（可演示界面、真实试点数据），否则差异化会被其内容淹没。

### 2.1 概念已无壁垒（头部共识证据）

QCon 上海 2026 会前直播中，**阿里**邹娟逐字描述：

> 「1.5 分钟短剧一集约 30 个镜头，一句台词从 3 秒改成 5 秒，可能影响前后 clip、口型、镜头长度、字幕时间甚至 BGM 节奏；系统若不知依赖关系，就会**改一处、坏多处**」，并提出「增量更新与局部重生成、只处理受影响部分」。

## 3. 核心概念模型

### 3.1 事实与命题

- **命题（Proposition）**：一条可判定真假的信息，例如「反派烧了仓库」。账本里的规范单位。
- **说法（Surface）**：同一条命题在剧本里的各种表达：「你三年前烧了那间仓库」「仓库的事」「那件事」「那笔账」。
- **使用（Use）**：某个角色在某一场**用到了**某条命题。
- **获知 / 信念（Know / Believe）**：某个角色在某一场**开始相信**某条命题。

#### 3.1.1 一条命题的粒度（**实测发现：这是全产品的隐含核心变量**）

> **一条命题 = 一个角色「可以知道或不知道」的客观事实。**

检验方法：能不能造出一句合法的「某人不知道这件事」？

| | 判据 | 例 |
|---|---|---|
| ✅ 是命题 | 有人可以不知道它 | 「苏婉伪造了沈父的遗嘱」「真遗嘱藏在怀表夹层里」 |
| ❌ 知识状态变化 | 它不是事实，是**认知事件** | 「沈知微**知道了**码头那件事」→ 属于 `knowledge_delta` |
| ❌ 声称 | 说话内容 ≠ 事实 | 「沈知微**说**遗嘱是假的」→ 属于 belief / claim |
| ❌ 同一件事的侧面 | 没有谁会「不知道」它 | 「陆见深站在岸边」 |

**这条规则不是美学偏好**，而是 R1 的硬需求：判据 `used_at(S,P,C) ∧ P ∉ mind(C)`
要求 `mind(C)` 里的元素**必须能被「知道 / 不知道」**。粒度选错，R1 要么误报要么漏报。

**为什么它是核心变量**（实测总结）：粒度同时决定了五件事 ——
抽取层输出规模、归并层判定难度、**候选集干扰强度**（`test-plan.md` P0-2
测到「难度上限只有 2」，就是它的另一面）、R1 的审计单元、依赖图 / 重做代价的节点。

**⚠️ 已知缺口：设计里缺一层。** 见 §5.2 与 `test-plan.md` §5.4 ——
第 1 层结构匹配与第 2 层 JEV **都只回答「是不是同一件事」**，
没有一层回答「**这几条细事实是不是同一个秘密**」。
后者是「审计单元」，粒度比「客观事实」更粗，需要额外的 promotion 层。

### 3.2 认知层：真相 ≠ 认知（**决定误报率**）

| 层 | 含义 | 例子 |
|---|---|---|
| **Fact** | 故事世界的客观真相 | 反派**没有**烧仓库（被陷害） |
| **Belief** | 角色以为是真，可能是错的 | 女主**相信**是反派烧的 |
| **Knowledge** | 信念与真相重合 | — |
| **False belief** | 明确的错误信念 | 女主以为男二是好人 |
| **Common knowledge** | A 知道 B 知道 C 知道… | 所有人都知道女主是继承人 |

**判定泄漏看的是角色心智，不是客观真相。**

错误写法（会误报）：

```
used_at(S, F, C) 且 learned_at(C, F) > S  →  泄漏
```

正确写法：

```
used_at(S, P, C) 且 P ∉ (knows(C) ∪ believes(C)) at S  →  泄漏
```

反例说明：女主**误信**「反派烧了仓库」（她看到了伪证），那她在第 3 集说这句话完全合理。按错误写法会判成泄漏，这是**误报**。

**副产品**：误信追踪本身是产品能力——谁在何时开始相信一件错的事、何时被纠正。这是短剧爽点结构（打脸、反转）的一部分。

### 3.3 事件同一性（不是相似度问题）

ontology 里的 **identity criteria**：两条事实在什么条件下是**同一个**事件？

> 如果剧本里反派**烧了两次仓库**（第 3 集、第 40 集），那「烧仓库」就是歧义的。不区分事件个体，账本会把两次纵火合成一条，泄漏判定直接错。

**事件同一性由结构化字段决定**：`(type, agent, patient, time_anchor)`。不能靠模型隐式判断——那是不稳定的，同一输入跑两次可能给出不同归并。

### 3.4 封闭世界假设（必须显式选定）

角色知识采用**封闭世界假设（CWA）**：剧本没交代他知道，就是不知道。否则「她可能通过别的途径知道了」会让**所有泄漏判定都不成立**，产品直接失效。

副作用：很多"显然知道"的事剧本不写（自己的名字、亲人的脸、常识），按 CWA 全成了「无源信息」→ 误报淹没用户。

**解法：默认知识层（default knowledge）**——角色必然掌握的内容，不参与泄漏检测。

### 3.5 事件演算（概念借鉴，不实现）

**Event calculus** 提供对口的形式框架：

- **Fluent**（随时间变化的属性）：`knows(agent, prop)`、`believes(agent, prop)`
- **Event**：`learns(agent, prop)`、`corrects(agent, prop)`
- **公理**：`initiates` / `terminates`
- **查询**：`holdsAt(fluent, t)`

「谁知道什么」就是一组 fluent，「获知」「误信被纠正」是事件。**只借鉴概念模型**（知识状态是被事件改变的量，而非一次性赋值），不实现完整形式系统。

**克制原则**：ontology 工程最著名的教训是 **Cyc**——巨型本体难以维护。**只建够回答下列能力问题的最小部分。**

### 3.6 能力问题（competency questions，schema 的设计起点）

1. 某角色在第 N 场知道 / 相信什么？
2. 某条命题第一次被交代来源是什么时候、通过什么方式？
3. 哪条命题从未被交代来源？
4. 哪些命题被埋下但从未被使用？
5. 某条命题在某场被使用时，使用者当时的心智状态是什么？

## 4. 数据模型

Postgres（Neon / Vercel Postgres）。**不上图数据库**，用递归 CTE。

### 4.1 叙事层

```sql
character        id, name, aliases[]                    -- 角色
script_scene     id, episode, scene_no, title,
                 raw_text, time_anchor                  -- 场次（time_anchor 处理闪回）
knowledge_fact   id, fact_key, fact_type,
                 agent, patient, time_ref,              -- 事件同一性的结构化字段
                 canonical_desc
knowledge_state  character_id, fact_id,
                 learned_at_scene, learned_via,         -- 获知
                 state_kind,                            -- know | believe
                 source_span, confidence
fact_usage       fact_id, scene_id,
                 used_by_character, evidence_span       -- 使用
alias            surface, context_key, target_fact_id,  -- 别名表（键 = 说法 + 上下文特征）
                 source, confidence, approved, evidence
waiver           finding_signature, reason, created_at  -- 否决
```

### 4.2 生产层（接入行业已有，不自造）

```sql
asset            id, kind(character|scene|prop|style), name
asset_version    asset_id, version_no, content_hash, params
shot             id, episode, scene_id, shot_no, prompt, status, duration_sec
shot_input       shot_id, asset_version_id
generation       id, shot_id, model, provider, cost, duration_sec, state
dependency_edge  from_kref, to_kref, edge_type, metadata
```

### 4.3 审计层

```sql
finding  id, kind, severity, fact_id, scene_id,
         evidence_span, reasoning_chain, status
```

### 4.4 三条关键设计决定

1. **`fact_usage` 与 `knowledge_state` 必须分开。** 前者是「这一场谁*用到了*」，后者是「谁*何时得知*」。泄漏判定是这两张表的差集。
2. **`time_anchor` 是必需的。** 短剧是闪回 / 重生 / 穿越最密集的剧种，「叙事顺序 ≠ 剧情时间」。不在数据模型里显式表达，后面一定返工。
3. **`alias` 的键是「说法 + 上下文特征」，不是「说法」。** 同一个「那件事」在不同上下文指不同命题。

## 5. 处理管线

```
剧本
 └─ 1. 分场 + 时间锚定          （闪回由模型推断，人可一键改判）
     └─ 2. 候选检索              （实体词 + 显著性 + 最近提及，从账本取少量候选）
         └─ 3. 逐场抽取 (map)     （当前场 + 候选 → 事实三元组；含指代还原）
             └─ 4. 事实归并 (reduce)
                 └─ 5. 账本更新    （写命题 / 心智 / 使用 / 别名）
                     └─ 6. 增量审计（只检查本场涉及的事实）
                         └─ 7. finding（带证据链）
```

### 5.1 第 2 步为什么必须独立存在

抽取器的输入**不是**「当前场景 + 全剧本」，而是「当前场景 + **从账本检索出的少量候选事实**」。这样同时解决三件事：长距离指代、成本、准确率——抽取器的任务从「理解全文」退化成「把『那件事』绑定到某个候选上」。

**这个环节的召回率是整个系统最关键的上游指标**：候选里没有目标命题，后面所有环节都救不回来。宁可多召回（让 judge 挑），不能漏召回。

## 6. 归并设计（核心难点）

### 6.1 为什么 embedding 不够

```
「仓库那场火」 vs 「仓库失火了」   → 语义相似度高，归并 ✓
「仓库那场火」 vs 「那件事」       → 语义相似度低（0.3–0.5 量级），但指同一件事 ✗
```

**embedding 衡量「语义相似」，归并要的是「指称同一」——这是两个不同任务。** 代名词和模糊指代的字面语义本身就是模糊的，信息不在这个句子里。

而且**编剧用模糊指代是刻意的**（悬念装置），所以模糊指代在短剧里是常态而非噪音。用 embedding 做第一层过滤器会**系统性漏报**，漏掉的正是编剧最用心埋的那些。

**正确做法：把重心从「归并」移到「抽取」。**

```jsonc
// 第 3 集：「你三年前烧了那间仓库」
{ "fact": "反派烧了仓库", "surface": "你三年前烧了那间仓库",
  "resolved_from": null }

// 第 12 集：「那件事」（上下文：反派问手下"仓库的事处理干净了吗"）
{ "fact": "反派烧了仓库", "surface": "那件事",
  "resolved_from": "S12-02 反派对手下说「仓库的事处理干净了吗」" }
```

两条 `fact` 字段一致 → **结构匹配即可归并，不需要 embedding**。`resolved_from` 天然是证据链。

### 6.2 三层路由

```
第 0 层  抽取（含指代还原）
第 1 层  结构匹配（确定性，零成本）
         (type, agent, patient, time_anchor) 全等 → 直接归并
第 2 层  候选绑定判定（JEV + 强模型）
第 3 层  人工确认
```

**强制升级通道**：命中模糊指代特征（代名词、「那件事 / 那笔账 / 那东西」、无实体名词）时，**提高接受阈值**（而非一律升级——一律升级会让 JEV 形同虚设）。

#### 6.2.1 ⚠️ 实测发现的缺口：缺一层 promotion（由 v1 端到端评测暴露）

第 1 层与第 2 层回答的都是**同一个问题**：「这两条描述的是不是**同一件事**」。
但产品需要的是**审计单元**，它比「客观事实」更粗：

```
细事实（抽取产出，第 0 层）
  苏婉伪造了沈父的遗嘱        ← 不同的行为
  苏婉调换了沈父的遗嘱
        ↓  promotion（缺失的一层）
审计单元
  「遗嘱被苏婉篡改」           ← 同一个秘密：谁不知道这件事
```

**判据不同**：第 1/2 层问「是不是同一件事」，promotion 问
「**这几条事实是不是同一个可被知道的事实**」。

| | 该并 | 不该并 |
|---|---|---|
| 苏婉伪造遗嘱 + 苏婉调换遗嘱 | ✅ 同一个秘密 | |
| 苏婉篡改遗嘱 + 陈默持有原件 | | ❌ 施事不同、可被知道性不同 |

**为什么必须补**：R1 的判据是 `used_at(S,P,C) ∧ P ∉ mind(C)`。
若账本停在「客观事实」粒度，一个秘密会被报成 N 条问题（「他不知道苏婉伪造了遗嘱」
「他不知道苏婉调换了遗嘱」），用户看到的是噪声；而依赖图也不该有
「陆见深站在岸边」这种节点。

**实测代价**（`test-plan.md` §5.3）：不做 promotion 时，14 条 golden 审计单元里
**9 条被拆成 2–3 条账本命题**，端到端准确率因此被压到 39.6%
（这个数字是**下界**，它度量的是粒度不一致，不是产品水平）。

**promotion 已实现并实测**（`src/extraction/promote.ts`，见 `test-plan.md` §5.6）：

| 指标 | 值 |
|---|---|
| 端到端 · 命题级 | 27/48（56.3%） |
| 端到端 · 审计单元级（无 promotion，用人工分组） | 34/48（70.8%）← 收益上限 |
| 端到端 · 审计单元级（promotion 实际产出） | **35/48（72.9%）** |
| 分群成对精确率 / 召回 | 80.0% / 77.8% |

⚠️ **单元级准确率会奖励过并**：分组越粗，误判越容易被算成「同单元」。
promotion 的 35/48 比人工分组的 34/48 高，**不代表它比人工分组好，只是更粗**。
所以这个指标必须与分群精确率一起看。

**实现选择：一次聚类，不是两两判定。** 第 1/2 层问「这两条是不是同一件事」（局部可判），
promotion 问「这几条是不是同一个秘密」—— 需要全剧语境，两两判定会丢掉它。
代价是不可增量（账本一变要重算），当前一次调用 $0.0019 / 0.4s，可接受。

**第 1 层为什么现在是空的**：P1-2 消融证明 `type/agent/patient/time_ref`
对判定零贡献，抽取层按最小范围没有抽它们 —— 所以确定性结构匹配暂时无字段可用。
这是**已知的待验证缺口，不是遗漏**：等 promotion 层稳定后，这些字段要从「判定证据」
重新定位为「结构匹配与影响传播的索引」（见 §6.4 的字段分级）。

### 6.3 JEV 的用法与局限

**JEV**（[JEV-as-a-Judge, arXiv 2609.26550](https://arxiv.org/abs/2609.26550)，TypeSafe AI）：decision-only judge，只返回**标签概率**，置信度决定接受还是升级。

**它适合归并的原因**：答案空间被限定（从候选里选一个），且**不需要生成解释**——证据来自抽取层的 `source_span`，不靠 judge 生成。

**论文数据**：

| 场景 | 结果 |
|---|---|
| 判决可从文本直接读出 | 逼近 GPT-6（差 3 分内），**成本 0.36%**，中位延迟 **0.15 秒** |
| 判决必须推导（数学 / 代码 / 逻辑） | **落后**；置信度正好标记这条边界 |
| 级联（接受高置信 + 升级其余，阈值预先冻结） | 1610 对 held-out 上**比 GPT-6 准 0.9 分，成本 41%** |

**必须知道的局限（论文自承，且正好命中我们）**：

- **style-adversarial pairs**：风格对抗对上的置信度路由会失效——正是「那件事」vs「仓库那场火」这类
- **reference-free prose**：无参考散文——剧本就是散文

**结论：JEV 是第一层过滤器，不是最终裁决。**

#### 6.3.1 查证结论（2026-10）

| 项 | 结论 |
|---|---|
| 形态 | TypeSafe AI 的**商业 API**（System One Models），**不能自托管** |
| 接入 | OpenRouter（`typesafe/jev-1.14`）、Vercel AI Gateway（`jev-1.14.0`）；另有本地 MCP server、LangChain、Langfuse 集成 |
| **定价** | **$0.044 / 1000 次判定**，中位延迟 **0.15 秒**（成本可忽略） |
| 原语 | **Choice / Score / Noul**；归并用 **Choice**（返回 `choice / probabilities / confidence`） |
| 开源替代 | **Laya**（Convai Innovations，Apache 2.0，open-weight + SDK）——论文明确其 **near chance on preference pairs**，**自托管路线目前不可用** |

**⚠️ 此处原判断「JEV 可能不够准」——已被实测推翻。** 保留论文数据如下作背景，但结论见其后。

| 模型 | RewardBench | **JudgeBench** | HaluEval | Final answer | 费用/1k |
|---|---|---|---|---|---|
| JEV | 92.5 | 78.6 | 87.3 | 94.0 | **$0.044** |
| GPT-5.6 Sol | 92.9 | **93.1** | 89.9 | 95.3 | $6.087 |
| GPT-6 Astra | 92.5 | **93.1** | 88.4 | 96.7 | — |

#### 实测结论（黄金集 v2，48 样本，别名时序过滤）

| 判定器 | 准确率 | 延迟/次 | $/1000 |
|---|---|---|---|
| rule（实体词匹配） | 16.7% | <1ms | 0 |
| **JEV v1（canonical + keywords）** | **91.7%** | **0.234s** | **$0.0446** |
| DeepSeek v4-pro（思考） | 95.8% | 5.68s | $5.86 |

**差距仅 4.1pp，而 JEV 便宜 131 倍、快 24 倍。**（JEV 实际单价已核实：$42 / 10 亿 input token = $0.042 / 百万。）

**根本原因：JEV 的瓶颈是「输入是否包含字面线索」，不是「推理能力」。** 两组对照实验：

| 改动 | 效果 |
|---|---|
| 候选换成结构化三元组（relation） | **±0pp** —— 压缩了字面信息 |
| 候选补上**典型表述**（keywords） | **+43.8pp** —— 补回了字面线索 |

**对本设计的含义**：

- **JEV 可用**，推荐做**级联第一层**：接受高置信（约 55–60%，准确率 96%+），其余升级给强模型 → **准确率持平、省约 56% 成本**
- **抽取层必须产出「典型表述」**（该命题在剧中出现过的说法）—— 这是 JEV 准确率的地基，而不是可选项
- **已知失效模式**：JEV 会**高置信地判 `NEW`** 来回避难题（`NEW` 是合法 choice，能穿过级联的第一道门），级联实现需专门防它
- 详见 [`rsi-log.md`](rsi-log.md) 的完整迭代记录与实验纪律

**安全风险**（[Datadog Security Labs, 2026-10](https://securitylabs.datadoghq.com/articles/jev-as-a-judge-how-counterfeit-policy-steers-jev/)）：在**不可信内容**里植入「伪造策略」可把 JEV 召回率从 **82.90% 打到 3.88%**。TypeSafe 文档承认 injected instructions、misleading framing、**"text arguing for its own classification"** 均会影响判断。

对本设计的含义：剧本进 JEV 的 state，而**台词常有很强的论证性**（角色自辩、说服、开脱），正属该失效模式。对策：

1. 剧本内容与判定指令在 state 里**结构分离**，不混在同一段文本
2. 用 **Choice**（有限选项），不让模型自由输出
3. 本产品是**审计工具而非安全网关**——被操纵的后果是漏报 / 误报，不是安全漏洞（风险等级中偏低），但仍须记录并防御

**顺序敏感性**：论文记录 95 次顺序翻转中有 3 次置信度 ≥ 0.9。**候选顺序必须固定**（按 salience 排序）以保证可复现。

**可直接沿用的阈值网格**：`{0.5, 0.6, 0.7, 0.8, 0.9, 0.95, 0.99}` + lower-bound rule（与 6.8 的「接受集零错误」等价）。

### 6.4 判定接口

**输入**

```jsonc
{
  "mention": {
    "surface": "那件事",
    "scene": "S12-02",
    // ⚠️ 必须是「所在行 + 前后各一行」的窗口，不能只给一句
    //    实测：一句 → 前后各一句，准确率 91.7% → 100%（多花 2.5% 成本）
    "context": "反派：仓库那边处理得怎么样了？\n手下：那件事早办干净了，没人知道。",
    "speaker": "反派", "listeners": ["女主"], "story_time": "T+3年",
    "kind": "vague_pronoun"                      // explicit_noun | repeated_surface | vague_pronoun
  },
  "candidates": [
    // 判定只需 canonical + aliases（= keywords）。其余字段是**索引**，实测不喂也不掉分
    { "id": "F-017", "canonical": "反派烧了仓库",
      "aliases": ["你三年前烧了那间仓库", "仓库的事"],
      // 以下仅供召回 / 同一性 / 影响传播使用，判定器可不见
      "type": "arson", "agent": "反派", "patient": "仓库", "time_ref": "三年前",
      "last_mentioned": "S03-07", "salience": 0.8 }
  ]
}
```

> **字段分级（实测确立，见 `test-plan.md` P1-1 / P1-2）**
>
> | 类别 | 字段 | 对判定的作用 |
> |---|---|---|
> | **证据** | `canonical`、`aliases`（典型表述）、`context`（**足够宽**） | 决定判得对不对 —— 全部提升都来自这里 |
> | **索引** | `type`/`agent`/`patient`/`object`/`time_ref` | **不喂判定器**；只用于召回、事件同一性、影响传播 |
>
> 推论：**抽取层打通端到端链路只需产出「命题表述 + 别名」**，
> 结构化字段可以晚做、做不全也不阻塞。

**输出（allowed output type）**

```jsonc
{
  "choice": "F-017",                    // 或 "NEW" / "UNSURE"
  "probabilities": { "F-017": 0.87, "NEW": 0.06, "UNSURE": 0.02 },
  "confidence": 0.87
}
```

**`UNSURE` 必须是合法选项**——答案空间里没有「我不确定」，模型会被迫在两个错误答案里选一个。这是很多 judge 用不好的根因。

### 6.5 判定指令模板

> ⚠️ **已知错位**：下面这版指令让模型用 `agent / patient / object` 做线索，
> 但 P1-2 消融显示这些字段**不喂也不掉分**。这个错位应作为 P2-1（指令措辞）的首个实验对象。
> 当前代码里的版本见 `src/judgment/prompt.ts`（带 `INSTRUCTION_VERSION`，便于追溯）。

```
判断「那件事」在这段上下文中指的是哪一条候选命题。

线索优先级：
1. 上下文中的实体词是否直接命中候选的 agent / patient
2. 说话人与候选的 agent 是否一致
3. 候选最近被提及的场景与当前场景的距离
4. 若没有被明确指向的候选 → 选 NEW
5. 若多条候选线索强度接近 → 选 UNSURE

重要：不要把"主题相似"当作"同一命题"的证据。
```

**最后一句是杠杆**：模型的默认倾向就是拿语义相似度当依据，而这正是本场景下会系统性出错的地方，必须显式禁止。

### 6.6 别名表（wiki 式累积）

```jsonc
alias {
  surface: "那件事",
  context_key: { scene_topic: "仓库", speaker: "反派" },   // 键 = 说法 + 上下文特征
  target: "F-017",
  source: "jev", confidence: 0.87, approved: true,
  evidence: "S03-07 你三年前烧了那间仓库"
}
```

三条规则：

1. **命中缓存 → 直接查表，不再调 JEV**（省钱的主要来源，且命中率随剧集推进递增）
2. **低置信 / UNSURE 不入表**，进人工队列——**不入表 = 不传播**
3. **保留 `source` 和 `confidence`**，使改阈值后可**批量重算**（RSI 循环能跑起来的前提）

### 6.7 命题合并：首版只建议不自动

发现 `F-017` 和 `F-042` 其实是同一件事，属于**破坏性操作**（要合并别名表、获知 / 使用记录，还要重算所有涉及这两条的审计结果）。**首版只出一份「疑似重复命题」清单让人确认。**

### 6.8 阈值标定

标定的对象是**三个参数**：

| 参数 | 含义 | 数量 |
|---|---|---|
| **τ** | 接受阈值 | 按 mention 类型分 **3 档** |
| **margin** | top1 与 top2 的间隔下限 | 1 |
| **M** | 最小候选数保护（可选） | 1 |

分档是**必需而非优化**：模糊指代的准确率天生低于显式名词。共用阈值，要么显式名词太保守（浪费升级预算），要么模糊指代太激进（误报）。

#### 黄金集构造

**样本形态**

```jsonc
{
  "id": "G-001",
  "mention": {
    "surface": "那件事",
    "context": "反派对手下说：仓库的事处理干净了吗",
    "kind": "vague_pronoun"
  },
  "candidates": ["F-003", "F-017", "F-042", "F-058"],
  "gold": ["F-017"],
  "note": "「仓库的事」是显式实体线索"
}
```

**六条纪律**

1. **候选必须是真实的 blocking 输出。** 手工挑候选（一个正解 + 几个明显错项）会让准确率**虚高**。
2. **负例必须有两类**：`NEW`（不指向任何现有候选）与 `UNSURE 可接受`（真歧义）。只标正解，会让模型学成「永远从候选里选一个」，学不会新建命题。
3. **gold 是集合不是单值**：真歧义时标多个，选中任一即算对。硬逼二选一会引入标注噪声。
4. **标注一致性必须先验**：两人独立标 20 条算 Cohen's kappa。**kappa < 0.8 就先修标注规范，不要继续标**——标注者都不一致的样本，模型永远学不会。
5. **采样贴近真实分布**：先**只跑 blocking**（不需要 judge）统计 mention kind / 候选数 / 相似度分布，再按分布采样。否则黄金集里 90% 是显式名词，标出的阈值在真实的模糊指代密集场景下失效。**这一步不需要任何标注，成本极低，但不能省。**
6. **接受统计现实**：样本量决定了能声称的准确率上限。

| 样本量 N | 零错误时准确率的 95% 置信下界 | 能得出的结论 |
|---|---|---|
| 50 | **94%** | 只能定一个**保守**阈值 |
| 150 | **98%** | 可以定稿 |
| 300 | **99%** | 才配得上「99% 准确率」这个说法 |

#### 扫描与选点

```
for τ in 0.50 … 0.99 step 0.01:
    接受集 = { 样本 | choice ≠ UNSURE 且 confidence ≥ τ 且 margin ≥ M₀ }
    记录 (τ, 接受集准确率, 接受率)
```

选点原则：**在「接受集零错误」的前提下，取接受率最高的 τ。**

用**错误数**思考而非错误率——N=50 时 1 个错误就是 2% 的差别，用百分比思考会自欺。

#### margin 与 τ 的关系

| 情形 | 判断 |
|---|---|
| confidence 0.45 / margin 0.05 | **升级**——top1 高是假象 |
| confidence 0.60 / margin 0.55 | **可接受**——margin 大而 confidence 中等，往往比前者更可信 |

标定时**三种方案都扫**（只用 τ / 只用 margin / 两者结合），比较**同等接受率下的准确率**。不要默认「τ 主 margin 辅」。

#### 分档样本分配

| 档 | 样本量 | 理由 |
|---|---|---|
| explicit_noun | 30 | 最容易，曲线陡 |
| repeated_surface | 30 | 中等 |
| vague_pronoun | **50** | 难点，且是产品价值所在 |
| 合计（含两类负例） | 约 110 | |

#### 冷启动：两步法

> **第 0 步（先做这个）**：用标定集**同时跑 JEV 与一个强模型**（GPT / Claude 级），比较两者在**归并任务**上的准确率。**若 JEV 明显落后，就直接换主方案**——不要因为它便宜（见 6.3.1），就假设它够用。这一步只要半天，却能决定整个级联的形状。

1. **第一步（半天）**：标 30–50 条，按真实分布采样 → 扫出保守阈值 → **偏差也要偏保守**（宁多升级）
2. **第二步（跑起来后）**：**waiver 就是免费的高质量标注**——每次否决产生一条**真实分布下**的负例，比人工标注更有价值。累积到 150+ 重新标定，逐步放开阈值

**这是 RSI 循环真正的数据来源：产品自己的使用，而不只是人工标注。** 这也说明为什么别名表必须保留 `source` 和 `confidence`——**不可批量撤销的判断，没法用来做实验**。

#### 防过拟合

1. **标定集 / 验证集分开**（60 / 40）
2. 标定集选 τ → 验证集**确认一次**，**不回头再调**
3. 验证集明显更差 → 说明标定集太小，**去补样本，而不是微调**
4. 阈值进配置并**带版本号**——改阈值 = 新版本，可回滚、可对比

#### 验收标准

| 指标 | 目标 | 说明 |
|---|---|---|
| **候选召回率** | **≥ 95%** | **上游指标，最关键**——候选里没有目标，JEV 再强也救不回来 |
| 接受的判定准确率 | 零错误（N=150 时下界 98%） | 归并错误会污染别名表，代价非对称 |
| 接受率 | ≥ 50% | 太低说明 JEV 形同虚设，成本没省下 |
| UNSURE 比例 | 10–25% | 太低 = 模型不会说「不知道」；太高 = 指令写得不清楚 |

**「候选召回率」要单独建一套标注**（人工标「正确的目标命题在不在候选集里」）。它是**唯一一个上游出错就无法挽救**的环节，比最终准确率更值得盯。

> **实测进展见 [`test-log.md`](test-log.md)**：截至 v1，最高准确率 **75%**（思考模式 · v0.2 数据），而**接受集准确率也只有 75%**，离上面的 98% 验收线仍有实质差距。
> 瓶颈已被定位在**黄金集构造**（UNSURE 样本标注不成立、F-002/F-009/F-010 区分度过低），而非判定器选择——两组策略完全不同、成本差 3.6 倍的配置在同一批样本上失败。
> 另一条硬约束由实测发现：**思考模式不支持 `temperature`，因此与 self-consistency 互斥**，必须在「更准」与「可路由」之间二选一。

## 7. Provider 抽象与降级

### 7.1 接口

```ts
interface JudgmentProvider {
  readonly name: string;
  judge(req: JudgmentRequest): Promise<JudgmentResult>;
}

interface JudgmentResult {
  choice: string;
  probabilities: Record<string, number>;
  confidence: number;
  provider: string;        // "jev-api" | "llm-judge" | "rule"
  latencyMs: number;
  costUsd: number;         // 单次调用即记账 → pi-telemetry
}
```

| 实现 | 用途 | 成本 |
|---|---|---|
| `RuleProvider` | **开发与黄金集回归测试**（实体唯一命中、字符串相等） | 0 |
| `JevApiProvider` | 生产主路径 | 按次 |
| `LlmJudgeProvider` | 降级（普通 LLM + JSON schema 约束） | 按 token |

**当前决定：使用 API，不做 JEV 本地部署。** 本地部署意味着要自己做**置信度校准**（小模型 logprob 系统性过度自信），而 API 服务方已完成这步。

`RuleProvider` 不可省：开发和黄金集回归**绝不能每次真调 API**，否则跑一轮就是一笔钱，且结果不确定。

### 7.2 路由逻辑

```ts
async function bindMention(mention, candidates) {
  const cached = await aliasTable.lookup(mention.surface, mention.contextKey);
  if (cached) return cached;                              // 0. 缓存

  const r = ruleMatch(mention, candidates);
  if (r.certain) return r;                                // 1. 本地规则

  try {                                                    // 2. JEV
    const j = await jev.judge(buildRequest(mention, candidates));
    telemetry.record(j);
    const tau = tauFor(mention.kind);                      // 模糊指代阈值更高
    if (j.choice !== "UNSURE" && j.confidence >= tau && margin(j) >= MARGIN) {
      await aliasTable.write({ ...j, approved: true, evidence: mention.sourceSpan });
      return { target: j.choice, source: "jev" };
    }
    return escalate(mention, candidates, j);               // 3. 升级
  } catch (err) {
    telemetry.recordFailure(err);
    return escalate(mention, candidates, null);            // 降级，不阻塞
  }
}
```

**两条降级链**：JEV 挂 → 直接升级（跳过 JEV）；强模型也挂 → 人工队列。**任何单点失效只让流程变贵或变慢，不会停。**

## 8. 审计规则

### R1 知识泄漏

```
used_at(S, P, C)  且  P ∉ (knows(C) ∪ believes(C)) at S
```

含**强制升级通道**：模糊指代条目提高判定阈值。

### R2 无源信息

```
used_at(S, P, C)  且  从未记录 P 被 C 获知或相信
```

**必须排除默认知识层**（角色必然掌握的：自己的身份、亲人的面孔、常识），否则误报淹没用户。

### R3 伏笔未回收

```
fact_type = setup  且  从未出现任何 usage
```

### 输出

每条 finding 带**完整证据链**：`used@S03-07 < learned@S12-02`，可点击跳到两句原文，可**一键否决**（写入 waiver，同类不再报）。

### 已知风险

- **可反驳是一等功能，不是补丁。** 学术上 NLI 类方法在「定位」任务准确率低到 0.04——误报会杀死这个产品。
- **时序锚点要人工可确认。** 闪回场景由模型推断，允许人一键改判。

## 9. 成本口径

### 9.1 用公式，不用行业数字

```
S = N × D × k × (1 + w)
k = 成功生成次数 ÷ 用上的段数
w = 改剧本导致的重生成（单独记原因码，不混进 k）
```

（[阿里云社区 2026-10-06](https://developer.aliyun.com/article/1768078)；原文自标「示例都是演示假设，不是行业数据」）

### 9.2 关键陷阱：k 不等于废片率

**审核失败的生成不计费**（火山方舟官方口径：「仅对成功生成的视频计费」），所以 `k` 把免费失败剔除了。而失败任务**真烧了 GPU 却在账单上显示免费**。

### 9.3 五个桶（必须分列）

| 桶 | 含义 | 是否算浪费 |
|---|---|---|
| 账单成本 | 实际计费的生成 | 基准 |
| **真实算力成本** | 含失败任务烧掉的 GPU（账单看不见） | 隐性浪费 |
| 审核拒答 | 平台审核拒绝 | 不可归因于创作者 |
| 探索性生成 | 试风格、试方案 | **不是浪费** |
| **变更重做 `w`** | 因剧本 / 资产改动而重做 | **本产品的主战场** |

### 9.4 行业数字一律不要引用

事实核查结论：**没有任何一条被多个真正独立来源佐证**。

| 说法 | 问题 |
|---|---|
| 「损耗率 30%」「算力占成本 50%」 | 出自南都采访的**600 人公司**，与「1.4 元/秒」（**7 人公司**）不是同一家，不可混用 |
| 「9 万元成本」 | 原文是「一部 **60 分钟**剧」，不能说「单集」 |
| 「平均生成 5 次」 | 原文自认是**演示假设** |
| 「8–12 轮抽卡」 | 纯 PR 稿；且那是「用其产品**之前**」的困境 |
| 「1.46 次/场」 | 厂商口径经转述，未注明统计时间与样本 |
| DataEye 0.16% / 1.3% | **不同阈值 + 不同分母 + 不同时间窗**，不可互换 |

**行业没有统一的「废片率」定义**（至少五种分母口径）。汇报时应说「行业无统一定义，我采用这个口径」——比抛一个查不到出处的数字有力。

### 9.5 成本控制的两个真正杠杆

1. **候选检索的召回质量**（少漏一次 = 少一次判定）
2. **别名表缓存的命中率**（命中一次 = 省一次调用）

成本从「本地推理免费」变成「按次计费」后，**缓存从性能优化升级为成本必需**。

### MCP 的可插拔定位

不要和 skill 生态竞争，要成为**它必须依赖的那一层**：账本做成 MCP server，让任何隔离上下文的 skill 通过工具调用查状态、报问题、写回 waiver。skill 负责「什么时候检查、用什么话术呈现」，账本负责「状态是什么、判据是什么、历史怎么追溯」。
