## 0. 怎么跑

```bash
npm run eval:rule                    # 零成本规则基线，不需要任何 key
npm run eval -- --provider openai    # 用 .env 配置的判定服务
```

关键环境变量（详见 `.env.example`）：`JUDGE_SAMPLES`（采样次数）、`JUDGE_THINKING`（思考模式开关）、`JUDGE_TEMPERATURE`。
级联模拟的阈值可用 `EVAL_TAU` / `EVAL_MARGIN` 覆盖（默认 0.8 / 0.15）。

评分口径：gold 是集合，选中任一即算对。`NEW` / `UNSURE` 也是合法答案。

## 3. 逐次记录

### 3.1 规则基线（v0.1）

`RuleProvider` 只做一件事：候选的 `patient` / `object` 字符串是否出现在 mention 文本里。

- **4/20（20%）**
- 12 条返回 UNSURE（无实体线索）
- **3 条被 `F-009` 抢走**——它的 `object` 是「遗嘱」，而该词在多处上下文出现，**高频词导致误命中**
- NEW 判不出来：规则层原理上无法区分「新命题」与「线索不足」（两者都是"没命中"）

**结论**：纯实体匹配不可用。但作为基线它证明了一件事——**NEW 的判定需要语义理解**。

### 3.7 JEV 接入与实测（v0.3）

**接入要点**（踩过的坑记在这里）：

| 项 | 结论 |
|---|---|
| 端点 | TypeSafe 直连 `POST https://api.typesafe.ai/v1/systemone`（另有 OpenRouter 中转 `POST https://openrouter.ai/api/alpha/decisions`） |
| 鉴权 | `Authorization: Bearer <key>`；key 来自 TypeSafe console，形如 `apikey_…` |
| 请求体 | `state` + `questions`，问题是 **choice** 原语，每个选项带一条 `criteria` 判据 |
| **`model` 是必填** | 缺省返回 **422**（`Field required`）。服务端实际解析到 `jev-1.13.0` |
| 响应 | `answers.<name>.{type, choice, confidence, probabilities}` + `usage.input_tokens` |

**结果：14/21（66.7%）**，延迟中位 **245ms**，三个关键负例**全对**。

**两个技术发现：**

**① `confidence` 与 `probabilities[choice]` 不同源。** 原始响应示例：

```json
"bind": { "choice": "F-009", "confidence": 0.21,
          "probabilities": { "F-002":0.02, "F-003":0.12, "F-009":0.34,
                             "F-010":0.01, "NEW":0.27, "UNSURE":0.24 } }
```

`choice` 与概率最高项一致（0.34），但 `confidence` 是 0.21。原 `marginOf()` 用 `confidence` 减分布 top2，因而算出**负数**。已修为**按概率分布计算 margin**（`types.ts`），`confidence` 保留为独立信号。

**② JEV 有非确定性。** 同一输入两次评测，G-004 的判定从 `NEW` 变成 `UNSURE`，多条样本的 `confidence` 也变了。

**级联模拟**（τ=0.8、margin≥0.15）：接受仅 **2 条**（准确率 100%），升级 19 条 —— **JEV 作为前置筛子只能过滤约 10%，级联省不下钱**。

**结论：JEV 在本任务上不够用**，符合论文预期（其在 JudgeBench 仅 78.6，而该基准测的正是「需要推理的判断」）。三个理由：准确率差 24pp、级联价值有限、**有非确定性**。

## 4. 关键发现

### 4.1 `margin` 是 JEV 的专属能力

OpenAI 兼容接口**不返回各选项的概率分布**，所以单次采样时 `margin` 恒为 1（无意义）。用普通 LLM 做 judge 只能用 self-consistency 近似；JEV 原生返回概率。

### 4.2 思考模式与 self-consistency **互斥**

DeepSeek 官方文档明确：**思考模式不支持 `temperature`**（设置了不生效）。推论：思考模式下 N 次采样会得到完全相同的结果，一致率恒为 1.0，self-consistency 退化失效。代码中已加启动告警。

| 路线 | 准确率（v0.3） | 速度 | 能否 self-consistency |
|---|---|---|---|
| 思考开 | **90.5%** | 10.3s | **不能** |
| 思考关 | 71.4% | 1.1s | 能 |

### 4.3 self-consistency 只能抓「犹豫」，抓不到「自信地错」

组 B 的 6 个错误中有 2 个是 `conf=1.00 margin=1.00`（G-016 / G-021），且 G-021 是 **3/3 一致地错**。它测的是「模型跟自己一不一致」，不是「模型对不对」。

### 4.4 **泛化命题会成为误命中的黑洞**

组 B 的 6 个错误里，**3 个被同一条命题吸走**：

```
G-007 → F-010      G-011 → F-010      G-016 → F-010
```

`F-010` 是三条相关命题里**最泛化的一条**（只陈述"遗嘱存在"，不含真伪、不含持有）。规则基线里也出现过同样现象（当时 `F-009` 吸走 3 条，因为它的 `object` 是「遗嘱」）。

> **命题的抽象层级会系统性影响归并——越泛化的命题越容易被误绑。**

这是候选集合的**结构问题**，不是模型问题。可行对策：候选排序时对泛化命题降权，或在抽取阶段避免产生过抽象命题。

### 4.5 **思考模式带来了元认知**（这是本轮最重要的发现）

| 关键负例 | 思考关 ×3 | 思考开 |
|---|---|---|
| G-020（完全无线索） | ✓ UNSURE | ✓ UNSURE |
| **G-021（有弱线索）** | ✗ **F-001，3/3 一致** | **✓ UNSURE** |

**当线索弱但存在时，非思考模式会抓住它并自信地用掉**；思考模式能判断出「这点线索不够」。

三个关键负例在思考模式下**全部判对**。这意味着 UNSURE 这条路径是**可达的**——不必靠外部机制硬造。

### 4.6 延迟数字不可跨批次比较

| 组 B | 延迟中位 | 成本/1000 |
|---|---|---|
| v0.2 | 7163ms | $2.09 |
| v0.3 | **1058ms** | $2.10 |

**成本几乎相同，延迟差 7 倍**——token 量没变，是网络或服务端负载波动。延迟不能用于跨批次对比。

### 4.7 评测工具曾有一个缺陷（已修）

旧版 `run-eval.ts` **只在错误清单里打印 conf/margin**，判对的样本不输出这两个字段 → 拿不到**完整的低置信清单**，而那正是决定级联升级名单的数据。

已修：新增「全量置信度分布」「级联模拟」「全量明细」三段，关键负例改为全部打印（原来只打第一条，导致 G-021 被漏掉）。

**另一个实现细节**：n=3 时 conf 只能取 1.00 / 0.67 / 0.33，因此 margin 只能取 1.00 / 0.33 / 0.00 —— **粒度太粗，撑不起精细阈值路由**。可能的解法是让模型**直接输出各候选的分数**（连续值、单次调用、不依赖温度），但需先验证其自报概率是否可信。

### 4.8 **判定稳定性实测**（本轮最重要的发现）

用 `eval/stability.ts` 对同一条样本重复跑 3 轮，量测可复现性：

| 判定器 | 准确率 | **判定一致率** | conf 波动(中位) | conf 波动(最大) | 延迟/次 |
|---|---|---|---|---|---|
| **DeepSeek 思考** | **90.5%** | **85.7%** (18/21) | 0.050 | **0.600** | 14.5s |
| DeepSeek 非思考 | 71.4% | **90.5%** (19/21) | **0.000** | 0.200 | ~1s |
| JEV | 66.7% | **90.5%** (19/21) | 0.040 | 0.110 | 0.24s |

> **准确率最高的配置，恰恰是最不稳定的那个。**

原因即 4.2 那条硬约束：**思考模式下 `temperature` 不生效**，无法像非思考模式那样用 `temperature=0` 压住随机性（后者 conf 波动中位 **0.000**）。

不稳定样本：

| 判定器 | 不稳定样本 |
|---|---|
| 思考 | G-004（UNSURE/NEW/UNSURE）、G-006（F-002/UNSURE/F-002）、**G-016（F-009/F-010/F-010，仅第一轮对）** |
| 非思考 | G-005（F-002/F-006/F-006，**两个都是 gold，属良性**）、G-006 |
| JEV | G-004（NEW/UNSURE/UNSURE，**三轮全错**）、G-006（NEW/NEW/F-002） |

**注意 `G-006` 在三种配置下都不稳定**——它处在决策边界上。

#### 对设计的直接影响

思考模式的 conf 波动最大到 **0.600**，意味着：

> **基于置信度的实时路由（「三道门」τ + margin + UNSURE）在思考模式下不可靠。**
> 同一输入重跑，置信度能从 0.9 掉到 0.3。

#### 三条由此确立的设计决定

| # | 决定 | 依据 |
|---|---|---|
| 1 | **用思考模式**（准确率优先） | 85.7% vs 71.4% 的差距远大于稳定性差距 |
| 2 | **判决落库冻结，永不重算** | 别名表存的是「**判决记录**」而非「待重算的缓存」——含 choice、概率分布、模型版本、输入哈希、时间戳 |
| 3 | **放弃基于置信度的自动升级路由**，人工复核改由界面驱动 | conf 波动 0.600，路由等于用一个会自己跳的阈值 |

第 2 条把 `design.md` 6.6 里「别名表保留 source/confidence」从好习惯**升级为架构必需**：既然重算会漂移，判决就必须是一次性、被记录的事实。

> **"可复现"不能靠选模型实现——三种配置没有一个是 100%。只能靠机制。**

## 6. 结论与下一步

### 6.1 当前最好成绩

**v0.3 · 思考模式 · 单次 = 90.5%（19/21）**，其中 `explicit_noun` 100%、三个关键负例全对。

成本 $8.10 / 1000 次，延迟 10.3s。

### 6.2 两个因素都显著（修正早期判断）

| 因素 | 影响幅度 |
|---|---|
| 黄金集质量 | **+11 ~ +15pp** |
| **判定器选择（思考 vs 采样）** | **+19pp** |

早期曾判断「瓶颈在数据而非判定器」——**数据修好后该判断已不成立**，判定器的比较现在才有意义。

### 6.3 JEV 的评估：已实测，结论是**不够用**

| 判定器 | 准确率 | 延迟/次 | 稳定性 | 1000 次成本 |
|---|---|---|---|---|
| DeepSeek 思考 | **90.5%** | 14.5s | 85.7% | $8.10 |
| JEV（实测） | 66.7% | **0.25s** | 90.5% | 待查 |
| JEV（论文口径） | — | 0.15s | — | $0.044 |

**三个理由**：准确率差 24pp、级联只能过滤约 10%（省不下钱）、**有非确定性**。

这**符合论文预期**——JEV 在 JudgeBench 仅 78.6（GPT-6 是 93.1），而该基准测的正是「需要推理的判断」。我们用实测验证了这条警示。

**但它的两个能力值得留下**：UNSURE 判定（3/3 全对）、低置信度信号（可用于标记人工复核，而非升级到强模型）。
