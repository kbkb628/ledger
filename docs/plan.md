> 上一版计划的问题是结构性的：它列的 A-1～A-4 全落在「评测器」这一个组件里，
> 而**改进提议器与搜索控制器根本没有规划** —— 那两块才是 RSI 区别于「人工调参」的地方。
>
> 回合纪律见 `rsi-protocol.md`；本文只定「每个组件现在什么样、缺什么、什么算完成」。

## 组件 1　任务执行器

**职责**：拿一个「版本」跑完整业务任务，产出**结果 + 执行轨迹**。

**现状**：`eval/run-eval.ts`、`run-e2e.ts`、`run-r1.ts` 三个脚本各跑一块，输出散落在 stdout。

**缺什么**：
1. **版本绑定** —— 基线 JSON 里没有记录模型名、prompt 版本、开关组合。
   下次抽取出不同账本时，无法判断差异来自模型漂移还是自己的改动。
2. **结构化轨迹** —— 目前只有汇总数字；失败样本的候选、置信度、分桶靠人眼从 stdout 里翻。
3. **跑什么是由我命令行决定的**，不是由「一个版本该跑哪些任务」这种声明决定的。

**要做**
- `src/rsi/version.ts`：算出版本指纹
  ```
  versionHash = sha256( 代码 commit + prompt 文本哈希 + 模型名 + 开关组合 )
  ```
- 执行器统一入口：`npx tsx eval/executor.ts --task judge|e2e|r1 [--task ...]`
  一次跑完该版本声明要跑的全部任务。
- 产出：`experiments/<expId>/result.json`（汇总）+ `trace.jsonl`（每个样本一行：判定、候选、置信度、失败分桶）

**验收**：任何一份产出都能回答「这是哪个版本跑出来的」，且能重放出同样的数字。

## 组件 2　改进提议器

**职责**：根据**失败证据**提出假设，生成**最小修改**。

**现状**：**完全靠我手工。** 那三条成因（`no_usage` / `masked_by_presence` / `delta_self`）
是我读 10 条输出逐条分析出来的。

**缺什么**：从「失败」到「候选改动」的映射没有任何机制，全在脑子里。

**要做（分两档，先做低档）**

**2a 规则库（无模型，确定性）**——每个失败桶绑定已知候选改法：

| 失败桶 | 候选改法 | 对应开关 |
|---|---|---|
| `no_usage` | 派生识别键匹配短引用 | `R1_SHORTKEY` + `R1_KEY_LEN` / `R1_KEY_FREQ` |
| `masked_by_presence` | 抽取区分「确立/提及」，`mind` 只从确立起算 | `R1_ESTABLISHED`（未实现） |
| `delta_self` | delta 指令禁止把说话人自己的话记成知情 | `R1_DELTA_SPEAKER`（未实现） |
| `wrong_proposition` | 改写级归并 / promotion 喂场景上下文 | 上游，需重生成基线 |
| `should_allow` | 默认知识层加规则（当事人 / 职责 / 公开事实） | `R1_AGENT` / `R1_PATIENT` / `R1_DUTY` |

提议器输出**受限形式**：`{ bucket, hypothesis, file, switch, params[], expectedEffect }`。
**最小修改 = 只动一个开关或一个参数**，不许大面积重写。

**2b 模型提议（后置）**——让 LLM 读轨迹提假设。
但输出必须同样受限（只能是开关+参数），否则既不可执行也不可回退。

**验收**：跑一次执行器，提议器打印「失败最多的桶是 X，候选改法为 Y（开关 Z），预期影响 …」，
且这个建议能直接被执行器执行。

## 组件 3　评测器

**职责**：跑测试，返回**结果 + 诊断 + 成本**。

**现状**：只返回 P/R。诊断（每条为什么错）靠人眼，成本只报了 $。

**缺什么**（这是上一版计划的 A-1～A-4，全部归到这里）

### 3-1　holdout 切分
- 标注扩到 **14 条**：10 dev + 4 holdout，`eval/leaks.json` 加 `split` 字段。
- `run-r1` 默认只报 dev，并打印「holdout 4 条已封存」；`--holdout` 才跑。
- **约定：holdout 只在「决定要不要翻默认值」时跑，跑一次记一次。**
- 4 条要覆盖不同桶（无源 / 时序 / delta 污染 / 应当放过），不能同类。

### 3-2　统一成本口径
- **两个成本都要报**：
  - 评测成本：`$` 与墙钟时间（决定一轮迭代多贵）
  - 指标成本：`cost = 误报数 × C_fp + 漏报数 × C_fn`
- 建议权重（**声明为假设，不是事实**）：`C_fp = 1`（一次人工复核）、`C_fn = 3`（一场戏返工）。
- 加**硬约束**：误报率 > 70% 直接判不可用，不论 cost 多低
  —— 误报真正的伤害是「让人关掉工具」，这一点权重表达不出来。

### 3-3　联合回归
- `npx tsx eval/regression.ts` 一次跑三组：判定层（91.7%）、端到端（60.4%）、R1 dev。
- 写入 `eval/baseline/regression.json`，与上一版比对输出 `↑/↓/=`。
- **回退红线（代码强制检查）**：判定层或端到端任一退 ≥2 条 → 必须回退；R1 cost 上升 → 回退或翻开关。

### 3-4　诊断分桶（给提议器供料）
对每条漏掉/误报自动归入一个桶（规则写死，不用模型）：
`no_usage` / `masked_by_presence` / `delta_self` / `wrong_proposition` / `should_allow`。
输出按桶计数降序：`本轮最大洞：no_usage（4 条）`。

**验收**：一条命令出三组指标 + diff + 分桶排序 + 两种成本；
分桶结果能对上我手工分的那三条成因。

## 组件 4　搜索控制器

**职责**：决定继续哪个分支、分配多少预算、何时停止。

**现状**：**完全没有。** 我是「看一次结果 → 想一个改法 → 跑一次 → 看数字」的线性循环，
做完一个候选就扔掉，没有分支树，也没有明确的停止条件。

**要做**
- **预算**（写进配置，不许超）：`MAX_ROUNDS`、`MAX_USD`、`MAX_WALLCLOCK`。
- **分支策略**：同一个桶一次提 **1–3 个候选**（不同参数档，例如识别键的
  `3-4字/频≤1`、`4字/频≤1`、`5-6字/频≤1`），全部跑完再挑，而不是试一个丢一个。
- **接受准则**（按顺序判定）：
  1. 触发联合回归红线 → 否
  2. 误报率 > 70% → 否
  3. `cost` 低于父版本 → 是
  4. 只在 dev 上达标 → 跑一次 holdout 确认；holdout 也达标才翻默认
- **停止条件**（任一满足即停）：预算耗尽 / `cost` 连续 2 轮不降 / 误报率达标 / 无新桶可攻。
- 产物：分支树写进实验库，**人只做最终批准**。

**验收**：控制器能自己跑完一个桶的 3 个候选、选出最优、并把「为什么选它」写进记录；
停不下来时能被预算强制停下。

## 组件 5　版本与实验记录库

**职责**：保存候选、父版本、修改内容、结果、发布状态。

**现状**：git（代码）+ `rsi-protocol.md` 手写表格 + baseline JSON。能回退，但**不结构化**。

**要做**：`experiments/` 目录，一条记录一个文件：

```jsonc
{
  "id": "exp-007",
  "parent": "exp-006",
  "commit": "8dbd447",
  "version": { "extractModel": "deepseek-v4-pro", "promptHash": "…", "flags": { "R1_SHORTKEY": "1", "R1_KEY_LEN": "3,4" } },
  "change": { "bucket": "no_usage", "file": "src/audit/r1.ts", "switch": "R1_SHORTKEY", "params": {} },
  "result": { "dev": { "P": 0.385, "R": 0.50, "cost": 11 }, "holdout": null,
              "regression": { "judge": 44, "e2e": 29 } },
  "evalCost": { "usd": 0.05, "seconds": 43 },
  "status": "candidate"      // candidate | accepted | rejected | released
}
```

- 分支用 git branch：`rsi/exp-007`。
- `status: accepted` 才允许翻默认值；`released` 才允许进 `main`。
- `rsi-protocol.md` 的回合表由这些记录**自动生成**，不再手写。

**验收**：任何一条结论都能追到「哪个版本、在哪个 dev/holdout 上、用什么成本」；
回退一个候选只需 `git revert` 或改开关默认值，记录里留下 `status: rejected` 与原因。

## 实施顺序（有依赖关系，不能乱）

```
组件5 实验库（schema+目录）
   ↓ 所有东西都要往里写
组件1 执行器统一 + 版本绑定
   ↓ 产出可重放的轨迹
组件3 评测器补全（3-1 holdout → 3-2 成本 → 3-3 联合回归 → 3-4 分桶）
   ↓ 产出诊断
组件2 提议器（2a 规则库；2b 模型提议后置）
   ↓ 产出受限的候选改法
组件4 搜索控制器（预算 + 分支 + 停止条件）
```

前三步做完就能开始真正的 RSI 循环；组件 2a 与 4 是让它**不再依赖我的手工判断**的关键。

## B. 五组件就绪后继续的既有计划

按「数据指向什么就做什么」排。桶的计数决定次序，但 B-3 不能无限延后。

### B-1　内核 · R1 层（由分桶驱动）

| 项 | 说明 |
|---|---|
| cause ②：抽取区分「确立」与「提及」 | `established_at` / `mentioned_at`，`mind` 只从确立起算 |
| cause ③：delta 不把说话人自己的话记成知情 | 指令加硬约束，成本极低 |
| `patient`（当事人 / 保管者知情） | 抽取加 `patients`，规则同 `agents` |
| **作者显式声明** | `ledger_declare`：前史 / 特殊能力（重生、穿越）/ 职责范围 —— **这三类永远无法从剧本推断** |
| 职责性知情、公开事实类型 | 依赖上一条，以及 `type` 字段 |

### B-2　内核 · 上游（真正的瓶颈）

端到端 60.4% vs 判定层 91.7% 的差距，主体在**抽取→归并**：同一事实被不同措辞抽成多条命题后没并上。

| 项 | 说明 |
|---|---|
| 改写级归并质量 | 「沈父将真正的遗嘱放在书房暗格里」与「书房暗格里有一份东西」被判 NEW |
| promotion 质量 | 小剧本上退化成 10 个单元素组；应把命题所属场景与邻近原文喂进去 |
| 说法/别名覆盖 | 已做「最短指代片段」（R 33.3%→100%），短引用匹配仍不足 |

**贯穿红线**
1. 任何改动必过联合回归，任一红线触发就回退。
2. holdout 只在决定翻默认值时跑，跑一次记一次。

4. **B-3 不能无限延后**：若 M1 超过两轮未达成，先抽一轮做演示页
   —— 内核缺口是收敛问题，产品不可见是存在性问题。
