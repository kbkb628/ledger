# RSI 协议：可回退、不带噪声

> 这份文档是**方法约束**，不是研究笔记。用户的要求是：**措施不能反而让效果变差、不能引入噪声、必须能回退。**
>
> 写成文档而不是记在脑子里，是因为这几轮已经踩过：改动一轮、数字变差、却分不清是"改坏了"还是"抽取抖了"。

## 一、三条纪律

### 1. 回退靠开关，不靠删代码

每个招式都留一个开关，**默认值 = 已测定的最优**。变差了一条命令关掉，不用 revert 一堆 diff。

当前开关（`eval/run-r1.ts`）：

| 开关 | 默认 | 作用 | 实测 |
|---|---|---|---|
| `R1_AGENT` | `1` | 施事知道自己做的事 | 误报 23 → 18（−21.7%）时确立 |
| `R1_PRESENCE` | `1` | 命题首见场景的在场者得知 | **冻结输入下 +33.3pp 精确率**（50.0% vs 16.7%） |
| `R1_UNITS` | `0` | R1 跑在审计单元层 | **在这份小剧本上无效**（promotion 退化成 10 个单元素组） |
| `R1_CHAR_HINT` | `0` | 归并判定时附人物别称表 | **变差**：P/R 66.7%/66.7% → 50.0%/33.3%，故默认关 |

> ⚠️ 注意「默认最优」这四个字：`R1_UNITS`、`R1_CHAR_HINT` 的开关**还在**，只是默认关。
> 删掉就无法在更大标注集上复验了。

### 2. 比之前先冻结上游

**这是最重要的一条。** 抽取和归并都调 LLM，有非确定性。同一套开关、只重跑抽取，实测抖动达 **33pp**：

```
--fresh 第一次：精确率 66.7% / 召回率 66.7%
--fresh 第二次：精确率 50.0% / 召回率 33.3%     ← 开关完全相同
```

冻结基线放在 `eval/baseline/pipeline-leak.json`（抽取 + 归并 + 人物表的产物，已提交）。

```bash
# 只变 R1 层，上游完全冻结 —— 这一份数字才可比
R1_CACHE=eval/baseline/pipeline-leak.json npx tsx eval/run-r1.ts --reuse
```

**涉及抽取/归并的改动（如抽取指令、归并提示）不能靠 `--reuse` 比较**，
必须重新生成一份基线并**两个都留着**，否则等于换了尺子又换被测对象。

### 3. 一回合只改一个变量

并且必须记进下面的回合表：**改了什么 / 用哪份基线 / 改前 / 改后 / 判定**。
判定只有三种写法：✅ 采纳（开关默认改为开）、❌ 回退（开关默认关掉，代码留着）、⏸ 待更大标注集。

### 第 6 回合：为什么先扩标注

3 条标注时每条值 33pp，与抽取抖动（同为 33pp）同量级，**任何改动都测不出来**。
扩到 10 条后每条 10pp，才分得清「改了有用」和「这轮抽取恰好不同」。

扩标注时加了一条硬规矩：**每条泄漏的「事实」必须被安排在更早、泄漏者不在场的场景里确立。**
否则「首见场景在场者得知」这条默认规则会把泄漏者自己的那句台词当成本事的确立点，
泄漏被自己掩盖（L-02 就是这么漏的）。

## 三、当前已知的硬事实（不受抖动影响的部分）

这些都是**冻结输入下**或**确定性**的结论：

1. **判定层是硬的**：人工账本 + JEV = 44/48（91.7%），3 轮稳定。
2. **抽取→归并是软的**：端到端 29/48（60.4%）。真瓶颈是**同一事实被不同措辞抽成多条命题后没并上**。
3. **promotion 在小剧本上退化成单元素组**（10 条命题 → 10 个单元），所以 `R1_UNITS` 无效。
4. **`R1_PRESENCE` 有效**：+33.3pp 精确率（+33.3pp 召回率时）。
5. **3 条泄漏标注太少**：每条值 33pp，与抖动同量级。**扩到 10–12 条之前，任何 <33pp 的改进都测不出来。**

## 四、任何新一回合的检查清单

1. 这回合改的是 **R1 层**还是**上游**？
   - R1 层 → 用冻结基线 `--reuse` 比较
   - 上游 → 先生成新基线，**并把旧基线一并保留**，两份都跑
2. 开关默认关着加进去，测完再决定要不要翻默认。
3. 数字变差就把默认改回关，**代码不删**，回合表记 ❌ + 原因。
4. 改动 < 33pp 时不改默认值，标 ⏸ 等标注集扩容。
5. 提交一个 commit，message 写回合编号与判定（回退 = `git revert` 或改开关）。

### 第 9 回合：`R1_ESTABLISHED` —— 收益真实，但暴露了评测器还缺一条

**假设**：泄漏台词本身也是一句断言，抽取会把它的场景当成事实首见点，
于是「首见场景在场者得知」把泄漏者自己的话变成他的知识来源 —— 泄漏被自己掩盖。

**同基线 A/B（冻结 v3，无噪声）**：

| 配置 | 报出 | 精确率 | 召回率 | cost |
|---|---|---|---|---|
| `R1_ESTABLISHED=0` | 5 | 60.0% | 30.0% | 23 |
| **`R1_ESTABLISHED=1`** | 4 | **100.0%** | **40.0%** | **18** |

精确率 **+40pp**、cost **−5**，远高于 33pp 噪声阈值。R1 侧这是迄今最大的一次改进。

**但触发红线**：抽取 prompt 加了 `established` 段之后，端到端单次重抽 **19/48**，
而冻结基线是 **23/48** —— 退 4 条。按「≥2 必回退」先关掉默认值（代码保留）。

**这一回合真正暴露的问题是评测器缺一条：**

> **单次 e2e 测量不可用于裁决上游改动。**
>
> 冻结上游后 e2e **3 次全是 23/48，零抖动**；但跨抽取的抖动是 **±6 条**。
> 所以「上游改动 → 重抽 → 比 e2e」这条路 **本来就测不出 4 条的差异**。

**同时撤回一个错误记录**：此前记录的「端到端 60.4%（29/48）」是**未冻结时的幸运抽样**。
真实基线是 **47.9%（23/48）**，冻结在 `eval/baseline/pipeline-e2e.json`。

**协议补充（从本回合起生效）**

1. **R1 层改动** → 冻结基线 + `--reuse`，可直接裁决（零抖动）。
2. **上游改动**（抽取/归并/promotion）→ 必须跑 **K≥3 次重抽取**，用中位数裁决，单次不裁决。
3. 冻结上游后的 e2e 数字才是可比基线；未冻结的单次数字一律不记录。

**下一步的更好实现方式**（不改主抽取 prompt，避免损害抽取质量）：
用**单独一次轻量 pass** 只判每条命题的 `established`，或用确定性规则（
「该命题的说法是否在某场出现在**非本人台词**的叙述/披露句中」）派生。

### 第 10 回合：联合回归上线，顺带抓出**配置漂移**

`npm run regression`（`eval/regression.ts`）：K 次重抽取 + 中位数裁决 + 红线检查 + 基线比对。

**第一次就跑错了，而且看上去像"崩了"**：judge 报 **23/48**。

原因：回归脚本没钉测量配置，judge 用的是默认
`JEV_CRITERIA_MODE=canonical + EVAL_CONTEXT=line + goldenset v2` ——
那是最早的 **v0 基线 47.9%**，不是已验证的 91.7% 配置。

> **教训：测量配置是测量的一部分。**
> 配置不进版本指纹、不进基线，就会出现「数字变了，但不知道是模型变了还是配置变了」。

修法：`TASK_ENV` 把每个任务的测量参数**钉死在代码里**，并写进基线文件。

**正确的基准（K=3，中位数）**

| 任务 | 各次 | 中位数 |
|---|---|---|
| judge（人工账本 + JEV，keywords + neighbors，golden v3） | — | **44/48（91.7%）** |
| e2e（抽取账本，`E2E_PAD=id`，golden v3） | 26, 26, 28 | **26/48（54.2%）** |
| r1（泄漏集 v3，10 条） | cost 23, 24, 24 | **P 50.0% / R 30.0% / cost 24** |

**又一个基线更正**：e2e 的 60.4%（29/48）与 47.9%（23/48）都是**未钉配置**时测的，全部作废。
真实基线是 **54.2%（26/48）**，e2e 抖动实测只有 ±2 条（26/26/28），不是之前以为的 ±6。

**裁决分工（从此生效）**

| 改动类型 | 方式 | 成本 |
|---|---|---|
| R1 层（只动开关） | 冻结基线 + `--reuse` | 秒级、零抖动 |
| 上游（抽取/归并/promotion） | `npm run regression` K=3 中位数 | 约 5 分钟 / $0.2 |

红线（代码强制）：judge 或 e2e 中位数退 **≥2 条** → 必须回退；R1 cost 上升 → 回退或翻开关。

### 第 11 回合：`R1_ESTABLISHED` 的正确裁决 —— 拒绝

用第 10 回合的 K=3 协议重裁（配置钉死、`--save` 不覆盖基线）：

| 指标 | 基线 | established | 判定 |
|---|---|---|---|
| judge | 44/48 | 44/48 | = |
| **e2e（K=3 中位数）** | **26/48**（26,26,26） | **23/48**（23,22,23） | **−3 → 红线** ❌ |
| R1 | P 50% / R 30% / cost 24 | P **100%** / R **20%** / cost **24** | cost 持平 |

**看到的关键机制**：精确率确实升到 100%，但**召回率从 30% 掉到 20%**，cost 一分没降。
原因：`established` 让在场者规则更保守（授知推迟到确立场），于是更多命题变成「无人知情」——
精确率上去了，但**本来就抓不到的泄漏更抓不到**。这是「用召回换精确」的典型，
而 cost 权重 `C_FP=1 / C_FN=3` 已经说明了这种交换不划算。

**上一轮的两处错误结论一并作废**：
- 「P 100% / R 40%」——单次抽取的幸运抽样；
- 「e2e 19/48 触发红线」——那次没设 `GOLDENSET`，跑在 v2 上，与基线不可比。

**这是第一个走完整回退流程的回合**：
假设 → 改动 → K=3 正确协议测量 → 触红线 → 回退（删 prompt 段 + 开关默认 false）→
**再跑 K=3 验证基线已恢复**（`44 / 26 / 24`，未触发红线）。

> 回退能被验证，是这套协议唯一真正的价值。之前「改了变差、又改回去、但不知道回没回去」的循环，到这里才真正闭合。

### 第 12 回合：事故 —— 回归卡死 30 分钟，暴露全项目没有 fetch 超时

K=3 回归第一次跑到一半彻底停住：进程 CPU ≈ 0、30 分钟无任何输出。
原因是抽取请求挂在网络上，而**所有 `fetch` 都没有超时**。

这类卡死比报错危险得多：报错会停下留痕，卡死只是让整条流水线静默停住。

修法：`src/util/http.ts` 的 `fetchWithTimeout(url, init, label, timeoutMs)`，
五处调用全部接入（抽取 / 人物表 / promotion / JEV / OpenAI 兼容），
默认 `HTTP_TIMEOUT_MS=120000`，超时抛出带 label 的明确错误。
验证：`HTTP_TIMEOUT_MS=1` 时 1.3 秒内报 `人物表抽取 超时（0s 无响应）`，不再永久等待。

### 第 13 回合：搜索控制器上线 —— 五组件闭环完成

`npm run controller -- --from-run <runId> [--bucket X] [--max-candidates N]`

它把「提议 → 执行 → 裁决」串成无人值守的一轮：

```
目标桶：no_usage（人工指定）
父版本：exp-009（P 50.0% / R 30.0% / cost 24）

▶ 候选 1/3  R1_SHORTKEY=1 {"R1_KEY_LEN":"3,4","R1_KEY_FREQ":"1"}
   P 33.3% / R 50.0% / cost 25 → reject（精确率退 16.7pp，护栏 >10pp）  exp-010
▶ 候选 2/3  {"R1_KEY_LEN":"4"}      → reject（退 20.0pp）  exp-011
▶ 候选 3/3  {"R1_KEY_LEN":"5,6"}    → reject（退 12.5pp）  exp-012

结论：没有候选优于父版本（3 个全被闸门拒绝）——这条搜索路径到此为止
```

**控制器刻意只自动执行「开关型」候选。** 上游型（改抽取/归并代码）它直接拒绝：

```
控制器：该桶的候选改法属于上游改动（R1_ESTABLISHED），控制器无权自己改代码。
  需人工实现后跑：npm run regression -- --k 3
  停止（不做无效搜索）。
```

这不是能力不足，是边界：控制器不是"自动改代码"，而是**把开关的搜索空间穷举掉**——
那恰好就是提议器 `variants` 字段存在的意义（同一桶的多个参数档）。

**它得出的结论比人更狠**：三个参数档全部被精确率护栏拒绝，且比 exp-007 时期更差
（基线精确率升到 50% 后，同样的绝对误报增量相对更伤）。所以「短引用匹配」这条路**已穷尽**，
需要换机制（例如只在同一审计单元内用识别键），而不是继续扫参数。

**顺带修了一个诚实性问题**：`--reuse` 时上游是缓存，`evalCost` 原本会重复计入历史抽取成本
（一轮虚假的 $0.17）。现在 `--reuse` 报 **$0**，控制器不会把历史成本算进本轮预算。

### 第 14 回合：留出集封存 + 首次标定（组件 3 补齐，五组件全部就位）

标注扩到 **14 条**：`eval/leaks.json` 每条加 `split: dev | holdout`，

## 五、回合的两种类型（**协议此前缺失的一类，是偏离 RSI 的根因**）

一次自我审计发现：五组件建好之后，我连续做了 5 项改动却**没有进实验库、没有记回合、也没有重建基线** ——
看起来在推进，实际已经脱离了 RSI 循环。

根因不是懒，是**协议只定义了一种回合**：

| | **能力回合**（capability） | **测量回合**（measurement） |
|---|---|---|
| 改什么 | 抽取 / 归并 / 判定规则 / 提示词 | **打分器、指标定义、置信区间、匹配算法** |
| 是否改变数字 | 是 | **是（但不代表能力变了）** |
| 是否需要 P/R 裁决 | **必须**（优于父版本才接受） | **不需要**（没有更好/更差，只有更对/更错） |
| 硬性要求 | 冻结基线 + 一回合一个变量 | **① 重建基线　② 声明哪些历史结论作废　③ 仍要进实验库（`kind: measurement`）** |
| 典型例子 | `R1_ESTABLISHED`（exp-008） | Wilson 区间、匈牙利指派、打分器版本化（exp-016～020） |

**缺了右侧这一列**，测量类改动就会被当成「顺手做的事」，于是出现：
仪器建好了、循环停了；基线与打分器错位；可比性闸门形同虚设。

### 已补的机制

1. `ExperimentRecord.kind?: "capability" | "measurement"`
2. 测量回合**仍必须进实验库**（exp-016～020 已补录，state=released）
3. 测量回合必须**重建基线**并写明「哪些历史结论作废」

### 本次审计的具体偏差与处置

| 偏差 | 处置 |
|---|---|
| 实验记录停在 exp-015，之后 5 项改动未入库 | 补录 exp-016～020，标注 `kind: measurement` |
| 回归基线保存在打分器版本化之前，`scorers` 为空 | **`--force-save` 重建基线**（judge 44 / e2e 26 / r1 cost 24 / real 9），首次写入 scorers |
| 可比性闸门因基线无 scorer 而失效，导致跨越打分器变更仍照常比较并宣布红线 | 已在协议中记明：**这是无效比较**；新基线已带 scorer，闸门从此生效 |
| `rsi-protocol` 停在回合 16 | 本文补记回合 17–20 的实质内容（见上表与 exp 记录） |

> **一条要记住的教训**：我把「建测量仪器」和「跑测量循环」当成了同一件事。
> 实际上**建仪器本身也要走回合**，否则仪器越多、越不知道自己在哪。

### 回合 22（测量回合）`context_protocol` 进结果契约

### 回合 24（能力回合）假设被否定 —— 廉价启发式修不了「泛化短说法误命中」

**原假设**（想做 `patient`，但先测量后发现更大池子是「泛化短说法」）：
这类误报能用长度阈值 / 出现频率 / 人名过滤修掉。

**数据直接否定了它**：

| 说法 | 长度 | 出现行数 | 结果 |
|---|---|---|---|
| 「就是他」 | 3 | 3 | ❌ 误报 |
| 「你不懂」 | 3 | 2 | ❌ 误报 |
| 「我顶不放心的还是大力的事」 | **12** | **1** | ❌ **误报** |
| 「暗格里那份」 | 5 | 5 | ✅ 正确 |
| 「两千三百万」 | 5 | 3 | ✅ 正确 |
| 「还有一口气」 | 5 | 2 | ✅ 正确 |

**长度和频率都无法区分**：12 字的整句也是误报，而 5 字的短引用反而正确（且出现次数更多）。

**真实机制**是**子串匹配**：长句「我顶不放心的还是**大力**的事」因为共享「大力」，
命中了另一人的命题「康顺子担心**大力**回来的事会连累王家」。廉价阈值不可能修掉这个。

**结论（写进 `testset.md` 与后续计划）**：
`buildUsages` 的字符串匹配到了能力上限，**真引用与巧合 token 重叠只能靠语义判断区分**。
正确做法是**复用已验证 91.7% 的判定层**做 usage 校验：
对每个候选 usage 问一次「这句话真的在引用这条命题吗」。
成本可估：`real` 259 个使用点 × ~0.2s ≈ 50s、约 $0.01 —— 完全可承受。

**判定 ❌ 假设被否定**（exp-024）。这不是失败，是**排除了一个方向**：
三次廉价尝试（人名过滤 ✓ 有效、长度阈值 ✗ 无效、频率 ✗ 无效）后，
方向已经很清楚 —— 下一步该是「判定层参与 usage 校验」这个**结构性改动**。

### 回合 25（能力回合）判定层参与 usage 语义校验 —— real 9→3

**假设**（由回合 24 的数据逼出来）：字符串匹配无法区分「真引用」与「碰巧共享词」，
应复用已验证 91.7% 的判定层，对每个候选 usage 问一次：
**「这句话是在指涉这条命题，还是只是碰巧共享词？」**

**做法**：`src/audit/usage-verify.ts`（`R1_USAGE_VERIFY`，默认开）。
候选为 `[该命题, UNRELATED]`，选 `UNRELATED` 则丢弃该使用点；
`UNSURE` 默认**保留**（宁可多报，也不掩盖真实泄漏）；调用失败也保留（不静默丢数据）。

**双目标 A/B（冻结基线，零噪声）**

| | dev | real |
|---|---|---|
| 关 | P 50% / R 30% / cost 24 | **7 条** |
| 开 | **完全不变**（36 使用点全保留，2 UNSURE） | **4 条**（丢弃 12 个假使用点） |

成本：253 次调用、**$0.0084 / 63s**。重建基线后 `real` 进一步到 **3 条 / 238 使用点**
（JEV 非确定性导致丢弃数略变 12→15）。

**净效果：`real` 从 9 → 7（回合 23 人名过滤）→ 3（本回合），dev 全程零回归。**

#### 本回合抓到的**自己的漏洞**

新增文件 `src/audit/usage-verify.ts` 改变了行为，但它**不在 `SCORER_FILES` 清单里** ——
于是打分器版本不变、可比性闸门抓不到。

> **教训**：「打分器版本化」不是加一次就完事，**新增影响结果的源文件必须同时登记进清单**。
> 否则闸门会给一个失效的绿灯。已修复（加入清单 + 把 `R1_USAGE_VERIFY`、`R1_MIN_SURFACE_LEN`、
> `R1_NO_SELF_ESTABLISH` 三个开关加入指纹）。

**新基线**：`judge 44/48`／`e2e 26/48`（各次 26, 26, 27）／`r1 P 50% R 30% cost 24`／**`real 3 条 / 238 使用点`**。

### 回合 26（能力回合）公开事实规则被**证伪**

**假设**：一条命题被 ≥K 个不同角色引用过 → 它是公开事实 → 视为常识。
（想用它消掉 `real` 剩下那 2 条「明天开张」）

**冻结基线 A/B（dev）**：

| 配置 | 报出 | 精确率 | 召回率 | cost |
|---|---|---|---|---|
| 关 | 6 | 50.0% | **30.0%** | 24 |
| K=2 | 1 | 0% | **0%** | 30 |
| K=3 | 3 | 33.3% | **10%** | 29 |

**证伪，而且是灾难性的**：根因是**循环论证** —— 「能引用它的人本来就知道它」，
于是所有**多人泄漏**都被当成常识掩盖掉了，dev 召回从 30% 直接清零。

**处置：删除实现**（不是关开关）。两条理由：
1. 规则被**证伪**，不是「无效」——留着会误导后来人；
2. 保留死代码会改变**打分器指纹**，强迫每轮重建基线，代价高于收益。

（这是对「代码不删、只关开关」的一次**有据例外**，理由记在此处。）

已 `git checkout` 还原，行为复核回到基线（P 50.0% / R 30.0%）。

**教训**：「公开事实」这个桶不能从**引用频次**反推。正确信号大概是
**显式的公开性证据**（抽取层标 `fact_is_public`，或叙述行里「当众宣布」类证据），
而不是统计学猜测。这条桶暂时**搁置**，等有更好的信号再做。

#### 一个流程摩擦（值得记）

删掉实现后，`scorerStamp` 仍与基线不一致 —— 因为期间 `scorer.ts` 的**清单变更**已提交，
文件内容与基线记录时不同。行为完全一致，但指纹变了。

> 这说明「按文件内容哈希」是**保守且有摩擦**的设计：任何代码改动（即使行为不变）
> 都要求重建基线。当前用 `--k 1 --force-save` 做**对齐**（只重签指纹，不重测），
> 并在记录里注明这是对齐而非重新测量。若摩擦继续变大，应改为**只哈希实际生效的行为**。

**当前基线（回合 26 后）**：`judge 44/48`／`e2e 25/48`（K=1 对齐时快照）／`r1 P 50% R 30% cost 24`／`real 3 条 / 239 使用点`。

### 回合 27（能力回合）`patient` 规则**无效**，已回退

**假设**：当事人知道自己被卷入的事（被卖/被换/被瞒），可用抽取层的 `patients` 字段建规则。

**抽取层确实产出了字段**：dev 25 条命题中 8 条有 patients，值也合理（林昭 / 沈父 / 何静）。

**但受控 A/B（冻结基线，零噪声）显示规则零效果**：

| 数据集 | `R1_PATIENT=0` | `R1_PATIENT=1` |
|---|---|---|
| dev | P 50.0% / R 30.0% / cost 24 | **完全相同** |
| real（同一份新缓存） | **3 条** | **3 条** |

**原因**：这些当事人本来就已被「施事」与「在场者」两条规则覆盖，新增规则**没有边际贡献**。

**另一条更重要的观察**：把 patients 段加进主抽取 prompt 后，茶馆首轮重建报告 **12 条**
（旧缓存 3 条）。该比较被抽取波动混淆、无法归因，但它与 exp-008（加 `established` 段
同样损害抽取）方向一致 ——

> **不应继续在主抽取 prompt 上堆字段。** 这是第二次观察到同一现象：
> 每加一段说明，抽取质量就抖一次。要加字段应当用**独立的一次轻量 pass**，而不是往主 prompt 里塞。

**处置：回退全部实现**（prompt / types / extractor / merge / r1 / run-r1），行为复核回到 P 50.0% / R 30.0%。

### 「当事人」桶的结案，与真正缺的东西

机制是对的，但**在当前账本粒度下冗余**。真正缺的是：

> **施事抽取本身的召回** —— 账本里 **41%（11/27）的命题 `agents` 为空**。
> 例如「有人从林昭父亲的账户转走了两千三百万」把施事抽成了「有人」，
> 于是真正做这件事的何静没有被授予知情。

这不是新字段问题，是**既有字段的抽取质量**问题。方向：提高 agents 的召回（或对「有人/某人」这类模糊施事做回指解析），而不是继续加字段。

### 回合 28（测量回合）第三条通道：审计结论回写 —— 并且它顺手暴露了两个自身缺陷

**问题起点（一次自我诊断）**：查 `ledger.json` 结构时发现**没有 `usages` 字段**。
于是每次审计都重算使用点、再做一遍 253 次语义判定（66s / $0.0084），
而**上一次的结论被直接丢掉**。

> wiki 的三条累积通道里，抽取和归并一直在做，**审计结论回写从来没做**。
> 它积累了剧本，却不积累判断。

**做法**：`src/audit/usage-cache.ts` 的 `resolveUsages`，接进 `ledger_audit`（MCP）与 `run-audit`（评测）。

| | 第 1 次 | 第 2 次 |
|---|---|---|
| 行为 | 253 次判定 → 保留 241 → 写回账本 | ♻️ 复用已存的 241 个使用点 |
| 耗时 | 67.6s / $0.0084 | **0.9s** |
| 报出 | 4 条 | **4 条（相同）** |

**dev 指标零变化**：P 50.0% / R 30.0% / 误报 3 条（与基线逐项相同）——
这条通道不动能力，只动「结论要不要留」。

#### 缺陷一：缓存**没有绑定账本内容**（差点造成静默错误）

版本戳只覆盖「打分器 + 上下文协议」，**不覆盖这份账本是谁**。
于是审计 A 剧本时，只要戳相同，就会复用到 B 剧本缓存里的使用点。
实测踩到：一次 `--reuse` 审计直接报 **0 个使用点**（还把它写回了缓存）。

> 一个只校验「规则版本」、不校验「输入是谁」的缓存，**是跨输入串味的**。
> 修复：加 `ledger = lg@<命题 id/规范说法/全部说法 的 sha256 前 12 位>`，
> 三项戳任一不符即作废重算。

#### 缺陷二：实验指纹漏了 5 个开关

`scorer.ts` 的 `R1_FLAGS` 有 `R1_USAGE_VERIFY` / `R1_MIN_SURFACE_LEN` / `R1_NAME_SKIP` /
`R1_NO_SELF_ESTABLISH` / `R1_ESTABLISHED`，但 `version.ts` 的 `RSI_FLAG_NAMES` 没有 ——
于是 `R1_USAGE_VERIFY=0` 的实验记录与基线**在库里长得一模一样**。

> 与回合 25 的教训是同一条：**新增开关必须同时登记进两处指纹**，
> 否则「这个数字是哪个版本跑出来的」这个问题会得到一个错误答案。

#### 这次改动**让 real 变了**：3 → 4，但不是能力变化

原来每次审计都重跑判定，结论不落盘，`real` 在 **3–4 之间抖动且不可复现**
（同一份缓存、同样的戳，两次跑出不同的丢弃数 12 / 15）。
现在冻结成 241 使用点 / 4 条，两次跑完全相同。

**所以本回合的处置不是「比较 P/R」，而是**：
① 重建基线（`real 3 → 4`，`usages 239 → 241`）；
② 声明作废：文档里所有「real 3 条 / 238–239 使用点」的旧数字不再可比；
③ 进实验库（`experiments/exp-028.json`，`kind: measurement`）。

这条 `real=4` 没有越过红线（红线是 +2），但**必读的一条**是：
`real` 此前作为「唯一有分辨力」的指标，其实**带着 ±1 的抽样噪声**；
冻结之后它才真的只有 4.6pp 的区间宽度。

|---|---|---|

### 回合 32（能力回合）把 should_allow 补上：误报收住了，漏报没动 —— 分辨率问题浮出水面

它能显形只在 holdout 那一侧。

**两条结论**

1. 许可层只能抓**时序**泄漏，抓不到**孤命题型无源**泄漏：`later` 要「更晚场次他也在场」，
   幻影命题只在泄漏场出现，条件永不成立。去掉它的自证只能用 `all`，而 `all` 会连
   「说话人总归知道自己在说什么」这条合法默认一起打掉（周管说老爷去世、何静说自己的钱、陈立报账）。
2. **dev 已失去分辨力**：10 条标注 ⇒ 一条 = 10pp，而 `--remerge` 同配置重复本身就在 tp 3/2 之间跳。
   +1~+2 级的许可层改动在 dev 上不可分辨；holdout 已解封两次，只剩最后一次。

**处置**：`R1_SHOULD_ALLOW` 默认关（dev 不可见、holdout 未达标），代码保留并注明「未通过的杠杆」。
下一步：把 should_allow 从词表升级成**判定层语义问询**（只对「许可被撤销」的候选问
「此人是否可能通过当事人/目击/被专门告知而合法知道」），让 `all` 能开而不炸精确率。
若这条仍不可分辨，就该回头做**测量回合**（扩标注集），而那超出「不动标注集」的约束 —— 要人来定。
### 回合 33（能力回合）should_allow 升级为判定层语义问询：误报砍半，但放过了一条真泄漏

`src/audit/leak-allow.ts`（`R1_LEAK_JUDGE=1`）：只对**已报出**的候选问一次
「此人是否可能通过①当事人/施事 ②目击 ③被专门告知 ④公开信息 而合法知道」，
`LEGIT` 放行、`UNSURE` **保留报出**（不静默放行）、判定失败也保留。

| 组合（冻结上游 `--reuse`） | dev |
|---|---|
| `all`（无 should_allow） | P 33.3% / R 60% / fp 12 |
| `all + shouldAllow`（词表版） | P 33.3% / R 60% / fp 12 |
| **`all + shouldAllow + 判定层`** | **P 5/11 = 45.5% / R 50% / fp 6** |

误报从 12 砍到 6（放行 6 / 存疑 2 / 保留 11），但**放行里含 1 条真泄漏**，
召回没涨（仍 50%），必要条件（P≥50%）差 1 条未过。

**成本是硬伤**：17 次调用 **218.6s / $0.09**，单次判定 ≈13s（openai-compat 思考模式）。
放到产品路径上，每次审计要多 1~4 分钟 —— 即使判据过了，这个形态也不能直接上。

#### 三回合的合并结论（in-scope 杠杆用尽）

| 杠杆 | 能做什么 | 为什么不行 |
|---|---|---|
| `R1_MERGE_EXACT`（逐字说法强制归并） | dev 只触发 1 次 | 指标零变化，无证据 |
| 许可层收紧（`all` / `single` / `later`） | `later` 在 dev +2TP 且不增误报 | holdout 上只 +1TP 却 +3FP；抓不到**孤命题型**无源泄漏 |
| 词表 should_allow | 吸收 2 条误报 | dev 上完全不可见（无前提角色、泄漏台词不自陈来源） |
| 判定层 should_allow | 误报砍半 | 放过真泄漏、召回不涨、**每次审计多 1~4 分钟** |

> **现在的瓶颈不是代码，是分辨力。** dev 只有 10 条标注（1 条 = 10pp），
> 而 `--remerge` 同配置重复本身就在 tp 3/2 之间跳；1 条级别的差异不可分辨。
> holdout 已解封两次，只剩最后一次。继续拧阈值就是在噪声上做实验 —— 这正是回合 24 的教训。

**处置**：`R1_LEAK_JUDGE` / `R1_SHOULD_ALLOW` / `R1_NO_SELF_ESTABLISH` 全部默认关，
dev 复核仍是 P 50.0% / R 30.0%（产品行为未变）。

把「许可收紧到 `all`」与「判定层豁免」同时打开，跑最后一次留出集解封：

### 回合 35（交付面回合）能装、能连：把 MCP server 打成包，并在三个位置验证它真的能起来

**这一回合不做能力裁决**：不动抽取、归并、R1 规则，不动标注集。dev 缓存、real 冻结账本、
holdout 全部没有触碰，三套数字一个都没变。它解决的是「卖点没有证据」：
`bin` 之前指向 `src/mcp/server.ts`，而那是 tsx 才能解释的 TypeScript —— 装到空目录里根本没有 tsx。

**做法**

1. `esbuild` 单文件 `dist/mcp.js`（保留 shebang，`@modelcontextprotocol/sdk` 留在 dependencies，
   `prepack` 自动构建），`bin → dist/mcp.js`、`files: ["dist", "README.md"]`、`engines: node>=20`。
2. 新增 `eval/npx-smoke.ts`：在**系统临时目录**（仓库之外、不设 `LEDGER_HOME`）里
   `npm pack` → `npx -y ./ledger-0.1.0.tgz` → 真 MCP 客户端走 listTools / ingest / check。
3. 产品缺陷：`JevProvider` 原是**模块级** `new`，缺 key 时 server 在 import 阶段就退出，
   客户端只看到 `-32000 Connection closed` —— 零信息量。改成延迟创建，异常落进那一次工具调用。
4. 记录缺陷：`experiments/exp-033.json` 带 UTF-8 BOM（Windows `Set-Content` 的默认行为），
   `JSON.parse` 抛错 → `nextExperimentId` 连整个实验库都读不出来。剥 BOM + 在读取处兜底。

**实测（本机）**

| 位置 | 结果 |
|---|---|
| 空目录 + `npx -y ./tgz` | 6 个工具 · ingest 13s · 默认账本落 `cwd/.ledger` · `check` 拦住一条、放过一条 —— 全过 |
| Claude Code | `claude mcp get ledger` → `Status: ✓ Connected`（装的是 `node_modules/ledger/dist/mcp.js`，四项 env 齐全） |
| DSH | 配置写进 `~/.dsh/profiles/desktop/cordis.patch.yml`；重启 harness 后 `mcp__ledger__ledger_check` 出现在工具表，模型侧调用返回 `leak: true`（E-002，沈知微 无知情记录）|

**三个坑（都值得记）**

1. Windows 上 `npx -y <绝对路径>.tgz` 会**静默什么都不做**（exit 0、无输出），客户端只能看到
   `-32000 Connection closed`；必须是相对 spec `./x.tgz` + `cwd`。
2. `claude mcp add` 的 `-e` 是**可变参数**：放在 `<name>` 前面会把 name 一起吃掉，
   报 `missing required argument 'name'`。必须 `<name> <cmd> <args> -e ...`。
3. DSH 的 MCP 配置要写进**正在跑的那个 profile** —— 本机跑的是 `desktop`，
   先写 `web` 白折腾一轮（无进程、无日志、无从判断）。

### 回合 36（测量回合）造一把有分辨力的尺子：把「幻影命题」单独量一次

**为什么先做测量**：上一轮（回合 34）判定不可达，两条根因之一是**仪器没有分辨力** ——
dev 只有 10 条标注（一条 = 10pp），同配置 `--remerge` 重复一次就在 tp 3 / 2 之间跳，
在这种尺子上做实验等于在噪声上做实验。P1 无论选哪条路，都得先有一把能分辨的尺子。

**做法**：`eval/script-phantom.md`（10 场）+ `eval/leaks-phantom.json`（16 条泄漏）。
同一个事实写**两条**泄漏，只有说法不同：

| 变体 | 写法 | 预期 |
|---|---|---|
| `phantom` | 换说法（「那把锁的密码」对「保险箱的密码是小姐的生日」） | 抽不出同一命题 → 被「首见场景在场者得知」自我掩盖 |
| `anchored` | 沿用确立场景的原话 | 归并挂到更早那条命题上 → 能抓到 |

一半对一半，所以读数**按变体分开报**（`run-r1` 加了分组报表），不汇总成一个 P/R。
另配 7 条 `must_not_flag`（告知方本人、当场被告知、施事本人）保护精确率。

**基线（`leaks-phantom@2#e4077fa003ee`；打分器 `r1@ab69114e28ee`；判定 openai-compat）**

| 变体 | 抓到 |
|---|---|
| phantom（换说法） | **1/8** |
| anchored（沿用原话） | **4/8** |
| 合计 | R 5/16 = 31.3% [14.2–55.6] · P 5/7 = 71.4% [35.9–91.8] · 误报 2 条 |

**这一回合真正的读数**：机制确认 —— **换了说法就基本抓不到**（1/8）。但更值钱的是后半句：
**即使逐字一致，归并也只有一半挂上**（`X-02`「保险箱的密码是小姐的生日」在 P-03 被判成 NEW）。
所以 P1-④ 的目标可以写成一个可兑现的数字：**anchored 4/8 → 8/8**，这条路径不依赖判定层、
不依赖新增规则，纯粹是归并层「同事实两种表述」的漏挂。

**两条误报的处置**：都在同一个命题上（陈述方本人陈叔、当场被告知的沈知微），已补进
`must_not_flag`；注意 `run-r1` 的**误报计数不受** `must_not_flag` 影响（只单独点名），
所以 P/R 数字不变 —— 补标注是为了让「设计错误」与「精度问题」不再混在一起。

**口径**：本集是**机制探针**，不是选版本的决策集（`split: dev`，但只与自己比）；
它每被用来对比一次，就要在这张表里记一次使用次数（本轮第 1 次：建立基线）。

### 回合 37（能力回合）归并层的确定性一层：长重合强制归并，anchored 4/8 → 7/8

**动手前先定两件事**（不然又是噪声上做实验）：两侧都跑 `--remerge`（冻结抽取、只重跑归并，
同一份抽取缓存），判定 provider 固定 `openai-compat`。

**改的是什么**：别名表存的是**整句台词**，所以「保险箱的密码是小姐的生日，老爷只告诉我一个人。」
与「保险箱的密码是小姐的生日，改不改都没意义。」逐字不等 —— 判官常判 NEW，同一事实于是拆成两条命题。
新命题的首见场景就是泄漏现场，`masked_by_presence` 当场给它发了许可。
`R1_MERGE_OVERLAP=1` 加一层确定性判据：两条说法共享一段 **≥6 字连续片段**（`R1_MERGE_OVERLAP_MIN`），
且这样的命题**唯一**时，直接挂上去、不交判官。

| | dev（`leaks@1`，remerge） | 幻影探针（`leaks-phantom@2`，remerge） |
|---|---|---|
| 关 | P 2/5=40.0% · R 2/10=20.0% · cost 27 · fp 3 | P 5/7=71.4% · R 5/16=31.3% · cost 35 · phantom 1/8 · **anchored 4/8** |
| 开 | P 3/6=50.0% · R 3/10=30.0% · **cost 24** · fp 3 | P 8/8=100% [67.6–100] · R 8/16=50.0% [28.0–72.0] · cost 24 · phantom 1/8 · **anchored 7/8** |

账本：幻影集 19 → 14 条命题（5 条重复命题被消掉），dev 25 → 24。
幻影集的两条误报也一起消失 —— 它们本来就是「同一事实两条命题」的副产品。

**裁决：默认关闭（status=candidate）**，三个理由都要写下来：

1. dev 上配对只翻转了 **1 对**（L-10），**McNemar 不一致对 < 6 ⇒ 不下结论**。方向为正、幅度未达显著。
2. 幻影探针是**机制探针**，按回合 36 定的规矩它不做版本裁决；它证明的是机制（anchored 7/8），不是终局判据。
3. **real 不能重测**：它算在茶馆那份**冻结账本**上，归并层改动在结构上动不到它；要量它必须重建账本，
   而那是新抽样，跨抽取比较被明令禁止。所以本回合**不能**声称 real 不退 —— 这是默认关掉的真正原因。

**留给下一步的**：翻默认前需要一次茶馆重建的 A/B（约 30 分钟）去量 real；
另外要盯一个风险 —— overlap 会在真实剧本上把两条**不同**事实并成一条（账本变小、误报也变小，看起来像改进），
所以「账本命题数下降」这件事本身既可能是修好、也可能是并过头，必须由 real 判。

**戳**：`R1_MERGE_OVERLAP` / `R1_MERGE_OVERLAP_MIN` 已同时登记 `scorer.ts` 的 `R1_FLAGS` 与
`version.ts` 的 `RSI_FLAG_NAMES`（这两处各漏过一次），r1 戳随之变化。

### 回合 40（测量回合）dev 接上第三条通道：从「每次重算」到「逐字复现」

但 `run-r1`（dev 的读数口）没有 —— 它每跑一次都重跑约 33–50 次语义判定。
后果不是慢，是**噪声混进判据**：同配置两次跑出不同 P/R 时，分不清是改动起作用还是判定抽样。

**改动（只改评测工具，不动打分规则）**：`run-r1` 改用 `resolveUsages`，
把使用点与三项戳（`scorer` / `contextProtocol` / `ledger`）回写进 R1 缓存；
任一戳变化 ⇒ 自动作废重算，不会拿旧结论冒充新结果。

**实测（同一份冻结账本，连跑两次）**

| | 使用点 | 判定调用 | P | R | cost | 误报 |
|---|---|---|---|---|---|---|
| 第 1 次 | 33 | 重算 33 次 / $0.0561 | 50.0% | 30.0% | 24 | 3 |
| 第 2 次 | 33 | **♻️ 复用缓存 0 次** | 50.0% | 30.0% | 24 | 3 |

**读法**：dev 的官方基线**没变**，但从这一回合起它是**可复现**的。
所以回合 31–38 里那些「两次 dev 读数差 1 条」的细微信号，从此应当按**未定论的判定噪声**处理；
要当信号，至少得 ≥2 条差异（这也和 McNemar 不一致对 <6 不下结论的规矩一致）。

**顺带修的一处输出**：以前只有「【usage 校验】保留 X / 丢弃 Y」一行，
看不出这次到底是复用还是重算；现在打一行【使用点】并直接写出「重算（N 次判定 $X）｜作废原因：…」
或「♻️ 复用缓存（0 次判定，结果逐字复现）」—— 「以为开了校验其实一直在重算」这类失效绿灯，
就是缺这一行才看不出来的。

### 回合 41（测量）e2e 从「中位数」改成「均值 + Wilson」

K=3 联合回归：e2e 各次 **27 / 25 / 25** → 中位 25、均值 25.67（53.5%）、**95% Wilson 39.6–66.8%**。
同一轮复现了其余三项：judge 44/48、real 7/269（与回合 39 冻结值一致）、r1 cost 各次 22/19/23。
以后 e2e 只报均值 + 区间：区间宽 27pp，任何 <10pp 的差异都在里面，单次读数没有裁决权。

过程里修掉一个真错：第一版写成 `wilson(round(mean*total), total)` —— 把比例又乘了一次 n，区间打出 `NaN–NaN`。
**数字全对、区间是垃圾**，正是「失效绿灯」的形态：报告看起来完整，却没有任何约束力。

### 回合 42（诊断）判定层 45/48 的三条错例：全是 UNSURE，不是选错

本轮 openai provider 得 **45/48 = 93.8% [83.2–97.9]**（基线 44/48 是 JEV 时代读数，差 1 条在噪声带内）。
三条错例：

| 样本 | 台词 | 候选 | 期望 | 得到 |
|---|---|---|---|---|
| G-001 | 你三年前在码头做了什么 @S02-02 | F-001,F-015,F-016,F-004 | F-001/F-015 | UNSURE |
| G-002 | 当年码头那件事 @S12-05 | 同上 | F-001/F-015/F-016 | UNSURE |
| G-041 | 那件事 @S12-05 | 同上 | F-001/F-015/F-016 | UNSURE |

结论：判定层剩下的误差**不是语义辨错，而是「指代短语 + 同一事件被拆成多条细事实」下的拒答** ——
和 R1 侧的 `masked_by_presence` 同一个根（回合 37/38 的归并层改动正是在治它）。
所以**不新增判定层规则**：回合 33 已证明判定层加规则会放过真泄漏；归并粒度做对了，这一桶应当自己变小。
级联模拟也支持「升级」这条路本身有效：接受 43 条全对（接受集准确率 100%），升级 5 条里 3 条原本是错的。

### 回合 43（能力，**否决**）should_allow 第三次尝试：问句不算断言 —— 拿下 4 条误报，代价是 2 条真泄漏

用同一份 usages/knowledge 做零成本隔离测量（只切开关，不重抽不重判）：

|---|---|---|---|
| 关 | 6 条 | 7 条 | 7 条 |

dev 因此 TP 3→2、P 50%→40%、R 30%→20% —— **红了 dev 红线，直接否决**，开关默认关。

根因写清楚：**「在问细节」与「在暗示自己知道」在词法上不可分**
（产品演示的招牌拦截「你三年前在码头做了什么？」形态完全一样，却是真泄漏）；
而「本职工作／公开事实」两类还需要世界知识。
这是 `should_allow` 桶的**第三次失败**（词表 → 判定层 → 问句），与回合 34 的裁决一致：
**在「不加语义判定、不引入世界知识」的范围内不可解**。产品侧的正式出口是 `ledger_waive`（人工豁免）。

> 戳变化（回合 43）：`R1_QUESTION_SKIP` 按纪律同时登记进 `scorer.ts` 的 `R1_FLAGS` 与 `version.ts` 的 `RSI_FLAG_NAMES`，
> r1 戳随之从 `r1@408749c3a15f` 变为 `r1@b91c0bcf23d5` —— 即使开关默认关，**戳变了**，已有使用点缓存在下次运行时会重算一次。

### 回合 48（交付面）演示片：把「数字可信」拍成片子，而不是念 PPT

**为什么用代码渲染而不是录屏**：录屏受网络与模型抖动影响，重录结果不同；而演示片要展示的恰恰是「可复现」。
所以目标文件由**同一个 `renderAt(t)`** 逐帧算出来（Canvas 2D + wasm H.264 编码，不依赖 ffmpeg），重渲一遍逐帧一致。

**成片**：`docs/film/ledger-film-v9.mp4` —— 238 秒 / 1920×1080 / 24fps / 141.9 MB。**本地保留、不入库**（`docs/film/` 已 gitignore）。
> 回合 49 补了产品图标与第 4 幕「产品亮相」（佐证之后 36.2–43.2s），后续各幕后移 7 秒，**当前成片为 245 秒 / 4 分 05 秒**。

十三幕，按「可信」这条线排：提问钩子 → 问题（编号三步 + 时间轴）→ **行业佐证**（三条逐字引用，附媒体与日期）→
技术点① wiki 建账 → 技术点② 生成/使用/回流 → check 拦放 → 审计与豁免 → 技术点③ JEV 同评测集对比 →
真实数据（2.6% / 4.2% + Wilson + 幻影探针）→ **RSI 五零件落在这台机器上**（含一次真实回合 30→37→38）→
六个工程亮点 → 如何使用（GitHub 下载 → 一行 MCP 配置 → agent 建账、文件长出来）→ 收尾。

**两处必须写在片子里的诚实标注**（都是评审最容易挑的）：

1. 佐证幕的行业引文讲的是**画面/主体一致性**，与我们做的**叙事知情一致性**不是同一层 —— 片中明文区分，并说明只用来证明「一致性是行业公认瓶颈」。
2. 「如何使用」一镜的界面是**简化示意**（非真实截图），画面左下角固定标注；数字仍取自真实运行（23 场 / 18 命题 / 15→14 条 / 14s）。

**修过的一个真 bug**：加入佐证幕后时间轴整体后移，但每个镜头内部还写着旧的绝对时间窗，于是后半段出现「只有字幕、画面空白」。
改成**镜头交界统一淡入淡出**（`renderAt` 按 BEATS 窗口算 FADE，所有绘制函数乘它），结构上不再可能出现空白段。

### 回合 50（测量）幻影集 8 对 → 30 对：先把尺子做细

**为什么先做测量**：v1 只有 8 对（phantom 1/8），一条 = 12.5pp、Wilson 区间 2–47% —— 在这种尺子上改任何东西都判不出真提升。

**做法**：`eval/build-phantom.mjs` 单表生成剧本与标注（30 个事实 × phantom/anchored 两条 = 60 条泄漏 + 6 条 `must_not_flag`，17 场）。
生成时就断言「说法在该场唯一命中、泄漏者不在知情者里」，写盘前不通过不出文件；`validate-goldenset.ts` 对 `variant: phantom` 不再报「原文里没有该说法」——
那正是 phantom 的定义（**把警告从噪声变成信号**）。

**基线（`leaks-phantom@2`，openai-compat 判定）**

| 变体 | 抓到 |
|---|---|
| phantom（换说法） | **13/30 = 43.3% [27.4–60.8]** |

v1 的 `1/8`、`7/8` 同时作废（剧本 10 → 17 场、事实 8 → 30 个，账本规模变了）。

**同回合的意外一课**：同一剧本连跑两次 `--fresh`，P-01 一次抽出 8 条命题、一次 14 条。

### 回合 51（能力）罕见词召回：让判官先看见，再谈判得准

**诊断**：`merge.ts` 的候选召回是字符 bigram 的 Dice（下限 0.15）。换说法的两句 Dice 常 < 0.15，
判官连候选都看不到 → 新建命题 → 首见场景在场者当场获得许可。**判定层一次没改**，改的是「判官能否看见」。

**做法**：`src/extraction/recall.ts` —— 在当前账本上算 2-gram 的 IDF，只有命中「足够罕见的共同词」才进候选（`R1_MERGE_RECALL=1`）。

| | 基线 | 加召回通道 |
|---|---|---|
| phantom | 13/30 | **18/30** |
| anchored | 21/30 | 21/30 |
| 总召回 | 34/60 | 39/60 [52.4–75.8] |
| 精确率 / 误报 | 91.9% / 3 | 92.9% / 3（同三条） |
| 归并花费 | $0.1594 | $0.2899（**+82%**） |

**判定**：`candidate`，默认关。
- 方向与机制完全一致：**5 条收益全部落在 phantom 那一半，零损失、零新增误报**；
- 但配对设计下 McNemar 不一致对只有 **5 对（5 vs 0），不足 6 → 无结论**（p ≈ 0.06）；
- 同时归并花费 +82% —— 一个没有证据支持的 +5，不值得翻默认。
- 顺手否掉的敏感性检查：只在「候选稀薄」时补（`R1_RECALL_TRIGGER=0.5`）→ 花费只降到 +58%，phantom 掉回 17/30。

**下一步按判据走**：不一致对 5 说明尺子还是粗，先把幻影集 30 → 60 对，再做同一实验；在此之前不再往召回层加机制（embedding、要素匹配都要等尺子能用）。
### 回合 52（测量）幻影集 30 → 60 对：仪器再翻一倍

回合 51 的不一致对只有 5 对（<6）→ 判不出。按「效应若真则不一致对随样本翻倍」的推断，把仪器从 30 对翻到 **60 对**（24 场 / 120 条泄漏 / 12 条 `must_not_flag`，仍由 `eval/build-phantom.mjs` 单表生成）。

**基线（v3，第一次跑，openai-compat 判定）**

| 变体 | 抓到 |
|---|---|
| phantom（换说法） | **17/60 = 28.3% [18.8–40.2]** |
| anchored（沿用原话） | **49/60 = 81.7% [70.0–89.4]** |
| 合计 | R 66/120 = 55.0% · P 66/71 = 93.0% · 误报 5 |

缝宽从 v2 的 26.7pp 拉到 **53.4pp** —— 新加的 30 个事实里 phantom 句改写得更彻底（`井壁上有三道划痕` → `井里的石头被划了三下`），说明 v2 的差额里有一部分来自「改写不够狠」。

### 回合 53（能力）同一实验在 60 对上重测：不一致对到了 9，但仍不显著

| | 基线 | 加召回通道 |
|---|---|---|
| phantom | 17/60 | **23/60** |
| anchored | 49/60 | 48/60（**-1**） |
| 总召回 | 66/120 | 71/120 [50.2–67.5] |
| 精确率 / 误报 | 93.0% / 5 | **95.9% / 3** |
| 归并花费 | $0.2634 | $0.5827（**+121%**） |

逐条：新抓 7 条（F-05-P、F-18-P、F-33-P、F-41-P、F-44-P、F-49-P、F-60-P），丢 2 条（F-23-P 换了候选被判成别的命题；F-31-A 是唯一 anchored 回退）。

**判定**：`candidate`，默认关。不一致对 9（过了 ≥6 的门槛），但 **p = 0.18**（只算 phantom 子组 p = 0.07）—— 都没到 0.05；同时花费 +121%。误报反而少了 2 条，说明候选变多没有把噪声带进来。

**本回合最值钱的一条方法结论**：连续两次翻倍仪器（8 → 30 → 60 对），效应稳定在「**+5~7 条、p≈0.07~0.18**」。按 28% → 38%、不一致率约 15% 反算，**80% 功效需要 150 对以上**（再一次翻倍要 2 小时 + 约 $1.5，还只能把 p 压到 0.05 边缘）。
→ 所以**问题不在样本量，在度量方式**：这条链上「候选有没有被召回」是**确定性**的（同一输入同一输出、零方差），根本不该用判官的噪声来量。下一轮改成两段度量：

1. **候选召回率**（确定性）：对每条泄漏，检查「确立命题的 id 是否出现在这条 draft 的候选表里」→ 60 对就能给出闭合结论，还能直接定位是哪条丢了候选；
2. **判官挂载率**（需要统计）：只在「候选已召回」的子集上看判官挂没挂上。

先做第 1 段（便宜、可闭合），再决定要不要为第 2 段付判官的钱。这也是本项目一贯的纪律：**先让仪器能判，再谈能力**。
